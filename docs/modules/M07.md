# M07 — Progress tracker

## Purpose

Replace the Google Sheet: a student-side weekly progress log, a
derived "weeks completed" / "reached the midpoint" view, the BR-08
actual-vs-planned duration variance flag, and a Focal Person overview of
every in-progress internship. Also gives row 8 of M04's transition table
(`IN_PROGRESS → DOCS_PENDING`) a real guard — recording actual dates is
the "finish and move to document submission" action, and until now it
carried no guard at all.

**Depends on:** M01 (`cases.actual_start`/`actual_end`, unused until
now), M02 (`case.progress_log_update`, declared, unused until now), M04
(the transition table/executor), M05 (`durationWithinBounds`'s
week-math, factored out here for reuse).

## Scope decisions this module makes

- **The progress log is a new table, one row per week, immutable once
  written.** `MASTER_PROMPT.md` gives no field-level shape for "weeks
  completed" or "mid-point check-in" — no `BR-` ID names either concept,
  unlike BR-07/08/09's precise field lists. A `ProgressLogEntry` per
  `(caseId, weekNumber)` (unique, so a week can't be silently
  overwritten) mirrors the old spreadsheet's natural shape: one row per
  week, a free-text note. Entries are never edited or deleted once
  created — the same append-only, audit-friendly default this codebase
  already applies to `case_events`/`audit_events`/`documents`; a
  correction is a new entry for a later week noting the correction, not
  a rewrite of history.
- **"Weeks completed" is a count, not a maximum.** `weeksCompleted =
  COUNT(entries)`, not `MAX(weekNumber)` — if a student logs week 1 then
  week 3, skipping week 2, counting by the highest number logged would
  overstate progress by one week they never actually reported on. No
  pure function needed for this; it's a single COUNT query.
- **"Mid-point check-in" is derived, not a stored flag.** Reached once
  any logged entry's `weekNumber` is at or past
  `ceil(plannedWeeks / 2)` — computed the same way BR-01's eligibility
  is computed, not self-declared or hand-set by a checkbox that could
  drift from the actual log.
- **Progress log entries are only accepted while `IN_PROGRESS`.**
  `MASTER_PROMPT.md` §2.1 says a Student "cannot edit any field after
  the case leaves `OFFER_SUBMITTED` except the progress log" — read as
  "the log stays open longer than everything else," not "forever."
  Logging *weekly progress* stops making sense once the internship work
  itself is over (`DOCS_PENDING` onward is the wrap-up/verification
  phase, not ongoing work) — `IN_PROGRESS` is the state that
  specifically means "conducting the internship" (step 5 of the eight).
- **Actual dates are recorded together, at the same action that fires
  row 8.** BR-08: "the system records planned dates at approval and
  actual dates at completion." "Completion" reads as the same moment
  the student finishes and moves to document submission — one action
  (`POST /api/cases/:id/complete-internship`) writes `actual_start`/
  `actual_end` to the case and fires `IN_PROGRESS → DOCS_PENDING`
  through the real executor, replacing that row's previously-empty
  guard list with `actualDatesRecorded` (presence + `end > start`
  sanity — *not* a 4-8-week bound check; that would contradict "flags
  variance," which implies actual duration is allowed to differ from
  planned, not blocked for differing).
- **The variance flag is computed on read, never stored.** Same
  "computed, not self-declared" principle as BR-01. Once both planned
  and actual dates exist, `computeDurationVariance()` (a pure function,
  reusing the week-math `durationWithinBounds` (M05) already had —
  factored into `src/server/progress/duration.ts` so both use one
  implementation) returns planned/actual week counts and whether they
  differ. Surfaced on `GET /api/cases/:id` (once actual dates exist) and
  on the in-progress overview.
- **`case.progress_log_update` covers both the weekly entries and the
  completion action.** Neither has its own row in `MASTER_PROMPT.md`
  §3's eighteen-row table — the same situation M05 hit with "open case"/
  "upload offer letter" sharing `case.open`. Reusing the one declared,
  previously-dead capability for both is the minimal-authority-surface
  reading; inventing a second capability the spec's table doesn't list
  would be adding permission surface it didn't ask for.
- **The in-progress overview is a new, dedicated endpoint, not just a
  reuse of M05's `GET /api/cases?state=`.** That existing route already
  lists cases by state, but returns raw case rows — a Focal Person
  overview needs the *progress summary* (weeks completed, midpoint
  reached) per case, which would otherwise mean N+1 requests (one list
  call, then one progress-log call per case). `GET
  /api/cases/in-progress-overview` returns each `IN_PROGRESS` case
  pre-joined with its computed summary in one call — the actual
  "replace the spreadsheet" deliverable, not a re-listing of what M05
  already gave.

## Data touched

One migration on the existing schema:

- New table `progress_log_entries`: `id`, `case_id` (FK), `week_number`
  (`CHECK (week_number >= 1)`), `note`, `created_by` (FK to `users`),
  `created_at`. `UNIQUE (case_id, week_number)` is the real enforcement
  of "one row per week, no silent overwrite" — application code doesn't
  need to duplicate that check.
- No other schema changes — `cases.actual_start`/`actual_end` (M01)
  already have everything the completion action needs.

## Business rules enforced

- **BR-08 (the actual-dates half)** — `actualDatesRecorded` guard on row
  8 (presence + sanity, not a bound check) and `computeDurationVariance()`
  (the "flags any variance for the Focal Person" half, computed on read).
- **§2.1's progress-log carve-out** — enforced by state-gating the
  upload/entry routes to `IN_PROGRESS` rather than trusting the client
  to know when it's allowed.

## API routes

All mutating routes call `requireCapability()` before touching data.

| Method | Route | Capability | Notes |
|---|---|---|---|
| `POST` | `/api/cases/:id/progress-log` | `case.progress_log_update` (STUDENT, owner only) | Body: `weekNumber`, `note`. Case must be `IN_PROGRESS`. `409` on a duplicate `weekNumber`. |
| `GET` | `/api/cases/:id/progress-log` | `case.view_own` / `case.view_any` | Entries plus `weeksCompleted`/`hasReachedMidpoint`. |
| `POST` | `/api/cases/:id/complete-internship` | `case.progress_log_update` (STUDENT, owner only) | Body: `actualStart`, `actualEnd`. Fires `IN_PROGRESS → DOCS_PENDING`. |
| `GET` | `/api/cases/in-progress-overview` | `case.view_any` (FOCAL/HOD/DEAN) | Every `IN_PROGRESS` case with its computed progress summary. |

`GET /api/cases/:id` (M05) is extended to include a `durationVariance`
field — `null` until both planned and actual dates exist.

## Screens

None — API only, consistent with M00–M06.

## Test list

- `unit/duration.test.ts` — `weeksBetween()` (the factored-out shared
  math) and `computeDurationVariance()`: matching durations report no
  variance, a shorter/longer actual duration reports the correct signed
  delta, no I/O.
- `unit/progress-summary.test.ts` — `hasReachedMidpoint()` against
  plain entry lists: below/at/above `ceil(plannedWeeks / 2)`, no
  database.
- `integration/M07_progress_log_entries.test.ts` — entries accepted only
  `IN_PROGRESS`; a duplicate `weekNumber` is rejected (`409`); ownership
  (`404` for another student's case); ordering and `weeksCompleted` on
  the `GET`.
- `integration/BR08_completion_records_actual_dates.test.ts` — the
  completion action rejects a missing/backwards actual date pair,
  succeeds with a valid pair, fires the real `IN_PROGRESS →
  DOCS_PENDING` transition, and `GET /api/cases/:id` afterwards reports
  the correct `durationVariance` for both a matching and a
  variant-duration case.
- `integration/M07_in_progress_overview.test.ts` — capability/ownership
  (`403` for a Student, `200` for Focal/HoD/Dean), and the returned
  summary's `weeksCompleted`/`hasReachedMidpoint` match a case's real
  logged entries.

## Done criteria

1. A progress log entry can only be recorded once per `(case,
   weekNumber)`, and only while `IN_PROGRESS` — both proven by test.
2. Recording actual completion dates fires a real, guarded transition —
   no direct write to `cases.state`.
3. The variance flag is computed, provably never a stored/self-declared
   value (same proof shape as BR-01's `BR01_eligibility_is_computed_
   not_stored.test.ts`).
4. The in-progress overview answers "weeks completed and midpoint
   status for every ongoing internship" in one call.
5. `docker compose up --build` succeeds from a clean volume state.
6. `/docs/PROGRESS.md` updated, M07 checked off.
