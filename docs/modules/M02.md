# M02 — Identity, sessions and authorisation

## Purpose

Give every later module the one thing it must never reimplement: a single,
server-side-enforced answer to "who is this, and what are they allowed to
do." Auth.js v5 handles authentication (who); a capability matrix
(`src/server/authz/matrix.ts`) and a `requireCapability()` helper handle
authorisation (what) — every mutating route in every later module calls
`requireCapability()` before touching data, per `MASTER_PROMPT.md` §9
"Access control." M02 also closes the account-security gaps called out in
§9 "Sessions and secrets": brute-force lockout, session invalidation on
password/role change, and password reset via email.

**Depends on:** M00 (containers), M01 (schema, migration pattern, the
`scit_app` runtime role — M02's new tables inherit its grants automatically
via M01's `ALTER DEFAULT PRIVILEGES`, no new grant SQL needed).

## Scope decisions this module makes

- **OQ-05** (BNU OIDC/SAML vs. self-managed passwords) is unanswered.
  Per §0.2, implement the most restrictive interpretation: self-managed
  argon2id credentials now. Auth.js's provider model means adding an OIDC
  provider later is additive, not a rewrite — `TODO(OQ-05)` marks the spot
  in `src/server/auth/config.ts`.
- **No self-registration route exists.** Per §2.6, only Admin creates
  accounts (a capability M03's roster import will exercise; M02 provides
  the mechanism — hashed-password storage — but not an account-creation
  route, since without a roster there's nothing to import). For this
  module's own tests, `prisma/seed.ts` gains a **dev-only** step that sets
  a fixed password on seeded accounts, clearly marked and never run
  against a database where `NODE_ENV=production`.
- **Password policy minimum length is 12 characters.** Not specified by
  `MASTER_PROMPT.md` or `PROJECT_DOCUMENTATION.md` and not listed as an
  open question (it's an implementation detail, not a policy question for
  the HoD) — 12 is a defensible default for argon2id-hashed credentials.
  Logged in `DECISIONS.md`, not `OPEN_QUESTIONS.md`.
- **Sessions are JWT-based, not database-backed.** Auth.js's official
  Prisma adapter expects its own `Account`/`Session`/`VerificationToken`
  shape, none of which this system otherwise needs (no OAuth providers are
  configured yet). Session invalidation (the actual §9 requirement) is
  achieved instead with a `tokenVersion` counter on `User`, checked afresh
  against the database on every request — see "Session and JWT design"
  below and `DECISIONS.md`.
- **No literal `/api/cases/*` route exists yet** (cases aren't reachable
  until M04's state machine and M05's screens exist). M02's own done
  criterion ("a student's session cannot read another student's case
  through any route") is proven against `Student`, the one ownable
  resource that already exists after M01 — `GET /api/students/:id`
  demonstrates the same `requireCapability()` + row-ownership pattern
  every later module reuses. This is *not* a preview of M05; it is
  scaffolding that gets superseded by real case routes and is not itself
  extended with case-shaped features.

## Data touched

Extends the M01 schema (new migration, not a new file — same
`prisma/schema.prisma`, same `prisma/migrations/` directory):

- **`users`** gains: `failed_login_attempts` (int, default 0),
  `locked_until` (nullable timestamptz), `token_version` (int, default 0,
  incremented on password change — this is what forces every other active
  session for that account to re-authenticate).
- **`password_reset_tokens`** (new table): `id`, `user_id` (fk), `token_hash`
  (unique — raw token exists only in the email, mirroring
  `supervisor_tokens`'s pattern from M01), `expires_at`, `used_at`
  (nullable), `created_at`. A partial unique index limits to one *live*
  token per user, same mechanism as M01's
  `supervisor_tokens_one_live_per_case`.

No changes to privilege grants are needed: M01's
`ALTER DEFAULT PRIVILEGES FOR ROLE CURRENT_USER IN SCHEMA public GRANT ...`
already covers tables created by this migration.

## Business rules enforced

None of BR-01 through BR-28 are owned by this module (those start at M03).
M02 instead makes the §2/§3 authority model and the §9 account-security
requirements real:

- **§2 "enumerated, not inherited"** — `matrix.ts` is the single source of
  truth both the API and (later) the UI read from; no code anywhere checks
  a role name directly.
- **§9 "No API route accepts a client-supplied role... for authorisation
  purposes"** — `requireCapability()` reads roles from the verified
  session (server-side, DB-refreshed every request), never from the
  request body.
- **§9 "Every mutating route calls `requireCapability()`... a route
  without it fails a CI lint rule"** — M02 adds that ESLint rule now, even
  though the only mutating routes that exist yet are M02's own
  (password-reset confirm). Later modules inherit the rule already wired.
- **§9 "Rate limits on login, password reset..."** and **"brute-force
  lockout"** (mentioned in M02's own line in §7) — both implemented; see
  API routes below.
- **§9 "Session invalidation on password change and on role change"** —
  see "Session and JWT design."
- **§9 "HttpOnly, Secure, SameSite=Lax cookies. Short session lifetime
  with sliding renewal."** — Auth.js cookie/session config.

## Session and JWT design

The JWT payload carries only `sub` (user id) and the `tokenVersion` at
issue time. On **every** request, the `jwt` callback:

1. Re-reads the user row (`token_version`, `disabled_at`, and current role
   names via `user_roles`) from Postgres by primary key.
2. If the row is missing, `disabled_at` is set, or the token's embedded
   `tokenVersion` no longer matches the row's `token_version`, the callback
   returns `null` — Auth.js treats this as an invalid session and the
   request is unauthenticated.
3. Otherwise it refreshes the token's `roles` claim from the freshly read
   `user_roles`, so a role change (e.g. Admin adds the FOCAL role to an
   account) takes effect on that account's very next request — no explicit
   revocation needed, because roles are never trusted from the stale JWT,
   only ever read fresh.

This costs one indexed primary-key read per authenticated request — at
department scale (§6 NFR: "under 2 seconds for 1,000 students") this is
immaterial, and it is what makes password-change and role-change
invalidation both true by construction rather than by remembering to call
a revoke function from N different places.

`sessionMaxAge` / `updateAge` give "short lifetime with sliding renewal"
(8 hours / 1 hour — reasonable defaults, not specified by the master
prompt, logged in `DECISIONS.md`).

## API routes

| Route | Method | Mutating? | Purpose |
|---|---|---|---|
| `/api/auth/[...nextauth]` | GET/POST | — | Auth.js handler: sign-in (credentials), sign-out, session/CSRF endpoints. |
| `/api/me` | GET | No | Returns the caller's own `{ id, email, roles }` from the verified session. No capability check beyond "authenticated" — everyone may read their own identity. |
| `/api/students/:id` | GET | No | `student.view_own` (Student role, `id` must equal the caller's own student row) or `student.view_any` (Focal/HoD/Dean). Returns 404 — not 403 — when a Student requests another student's id, so the route never confirms *which* ids exist to an unauthorized caller. |
| `/api/auth/password-reset/request` | POST | Yes* | Body: `{ email }`. Always responds `200` regardless of whether the email exists or the account is disabled — prevents user enumeration. If a real, enabled account matches, creates a `password_reset_tokens` row and emails the raw token as a link. Rate-limited per IP. |
| `/api/auth/password-reset/confirm` | POST | Yes | Body: `{ token, newPassword }`. Validates the token's hash/expiry/unused state, enforces the 12-character minimum, hashes the new password, increments `token_version` (invalidating every other active session), marks the token used. |

\* Neither password-reset route calls `requireCapability()`, and that's
correct, not an oversight: `requireCapability()`'s contract is "identity
must already be authenticated," but the entire point of password reset is
recovering access *without* being authenticated — there is no capability
an anonymous caller could hold that would make sense here. Proof of
authorization for `confirm` is the possession of the emailed token, not a
role. The CI lint rule (below) therefore excludes `src/app/api/auth/**`
by path — the same reason the Auth.js handler and a future login route
are exempt. This exclusion is the rule's only carve-out and is narrow and
named, not a general escape hatch.

## Capability matrix additions

`src/server/authz/matrix.ts` encodes the full §3 table (eighteen
capabilities) even though most have no route to call them from yet
(`grade.award`, `restart.countersign`, etc. — M09/M10/M11's job). Building
the matrix once, completely, now means those modules configure a route,
not a capability. Two capabilities exist solely to support this module's
own demonstration routes and are documented as such in the file:
`self.view` (any authenticated role) and `student.view_own` /
`student.view_any` (the stand-in proven here, superseded in spirit — not
in code, the mechanism doesn't change — once M04/M05 add
`case.view_own`/`case.view_any`).

## Screens

None with a UI yet — Tailwind/shadcn sign-in form is cosmetic and not
this module's point. A minimal, unstyled credentials sign-in page
(`/login`) exists only because Auth.js's `pages.signIn` config
(src/server/auth/config.ts) needs a real page to point to; M13 replaces
it with the real designed screen. API routes never redirect on 401 —
they return JSON, which is what every M02 route does.

## Test list

- `unit/password.test.ts` — argon2id hash/verify round-trip; wrong
  password rejected; hash is never the plaintext.
- `unit/matrix.test.ts` — every one of the eighteen §3 capabilities maps to
  exactly the roles §3 specifies; a role not listed for a capability is
  denied.
- `unit/require-capability.test.ts` — throws for a session lacking the
  capability; passes for a session holding it; never inspects a
  client-supplied role field.
- `integration/M02_no_cross_student_read.test.ts` — the named done
  criterion: a Student session requesting another student's `/api/students/:id`
  gets 404; requesting their own succeeds; Focal/HoD/Dean sessions can
  read any student.
- `integration/M02_login_lockout.test.ts` — 5 consecutive failed logins
  lock the account for the configured window; a 6th attempt with the
  *correct* password still fails while locked; succeeds after the window
  (using an injectable/fake clock, not a real wait).
- `integration/M02_session_invalidation.test.ts` — issue a token, change
  the password (or flip a role), assert the *old* token is now rejected by
  the `jwt` callback's DB re-check.
- `integration/M02_password_reset_flow.test.ts` — request issues one live
  token (second request before use replaces, not duplicates, per the
  partial unique index); confirm with a wrong/expired/reused token fails;
  confirm with a valid token succeeds and invalidates prior sessions.
- `integration/M02_no_role_from_request_body.test.ts` — negative security
  test: a request body carrying `{ role: "ADMIN" }` or similar has zero
  effect on the capability check; authorisation only ever reads the
  server-verified session.
- CI lint: a new ESLint rule (or `eslint-plugin-security`-adjacent local
  rule) fails the build if a route handler under `src/app/api/**/route.ts`
  performs a Prisma mutation without a preceding `requireCapability()`
  call in the same function.

## Done criteria

1. Auth.js v5 credentials sign-in works against argon2id-hashed passwords
   stored in `users.password_hash`.
2. `src/server/authz/matrix.ts` is the only place any capability-to-role
   mapping is declared; `requireCapability()` is the only way a route
   checks it.
3. An integration test proves a student's session cannot read another
   student's row through `/api/students/:id` (the current stand-in for
   "another student's case," per the scope note above).
4. Password change and role change both invalidate previously issued
   sessions, proven by test, not just by reading the callback code.
5. Brute-force lockout and the login/password-reset rate limits are both
   enforced and tested.
6. The CI lint rule requiring `requireCapability()` on mutating routes
   exists and is proven to fail on a deliberately-broken example route in
   a test fixture.
7. `docker compose up --build` still succeeds from a clean volume state.
8. `/docs/PROGRESS.md` updated, M02 checked off.
