# M14 — Hardening, backup and handover

## Purpose

The final module (§7). Its own done-criterion doubles as the whole
project's acceptance bar (§11): every BR-01 to BR-28 has a passing
named test, the §9 security checklist is demonstrated live, a backup
taken on one machine restores correctly on another, and the runbook is
complete enough that a new administrator can perform every operational
task from it alone.

## Two real, pre-existing gaps found auditing for "every BR has a passing named test"

Before any hardening work, an audit of every `BR-XX_*.test.ts` file
against §4's full BR-01 to BR-28 list found two rules with **no
implementation anywhere in the codebase**, not just no test — a real
gap in modules already marked complete, not a testing oversight:

- **BR-03** — "A student cannot be marked graduation-eligible without a
  `CLOSED_PASS` case or an approved waiver." No route, field or
  function anywhere computes or exposes this. Fixed:
  `isGraduationEligible()` (`src/server/roster/graduation.ts`), a pure
  predicate mirroring BR-01's own "eligibility is computed, never
  stored" precedent — `true` iff the student has any `CLOSED_PASS` case
  or any `Waiver` with `outcome: GRANTED`. Surfaced as an additive field
  on the existing `GET /api/students/:id/eligibility` route (M03)
  rather than a new endpoint.
- **BR-05** — "Each semester... has a configured document submission
  deadline. Cases missing deliverables at that deadline are flagged,
  not auto-failed." `semesters.document_deadline` has existed since M01
  with a doc comment naming M07/M09 as the module that would build the
  sweep — neither did. Fixed: `findDeadlineMissedCases()`
  (`src/server/roster/deadline-sweep.ts`), the same "computed at query
  time, never a stored flag or an automatic transition" pattern BR-27's
  SLA escalation and M13's overdue-eligibility list already established
  — a case is "missed" if its semester's deadline has passed and it
  hasn't yet reached `PENDING_VERIFICATION` (all three deliverables
  gathered). Surfaced on the HoD dashboard (M13) and via a daily
  BullMQ sweep reusing M12's notification infrastructure (one email to
  every `FOCAL` user per newly-missed case, deduplicated the same way
  BR-27's own sweep is). Never transitions the case — "flagged, not
  auto-failed" is enforced by construction: nothing in this path calls
  `executeTransition()`.

Both are real, substantive implementation gaps this module closes with
the same rigor as any other module's business logic — not just a
checklist tick.

## §9 checklist: already satisfied vs. new this module

Most of §9 was already built as a side effect of earlier modules'
own correctness requirements. `docs/SECURITY_CHECKLIST.md` is the full,
demonstrated mapping; the summary:

**Already real, cross-referenced to existing tests:** audit_events
append-only (M01/M09), `cases.state` trigger-guarded (M01/M04), grade
immutability + reversal (M09), no client-supplied state/role/grade/user
ID for authorization (established throughout, BR-25/§9's own "identity
comes from the session" rule), server-generated timestamps, every
mutating route capability-gated (custom ESLint rule since M02),
UUIDv7 resource IDs (M01), row-level ownership checks ("404, not 403"
pattern, every module M05 onward), upload validation by extension +
magic bytes + MIME + ClamAV (M06), UUID storage filenames / no path
traversal (M06), authenticated downloads with `Content-Disposition` +
`nosniff` (M06), documents never deleted (M06), HMAC-signed/hashed/
single-use supervisor tokens (M08), rate limits on login (DB-backed
lockout, M02) / password reset (M02) / supervisor token submission
(M08), students see only their own data + no student directory
(established throughout), evaluation comments hidden from students
behind a config flag (M08), no document contents/tokens/passwords/full
evaluation text in logs (established throughout).

**New this module:**
- Rate limiting on file upload (§9 names it explicitly; the three
  upload-accepting routes — offer letter, completion certificate,
  waiver evidence — had none).
- Full CSP (nonce-based, no `unsafe-inline` on `script-src`), HSTS,
  and the remaining headers Caddy's own M00 comment explicitly deferred
  ("M14 owns the full CSP, HSTS and remaining security headers").
- CSRF protection via Origin-header validation middleware — Auth.js's
  own sign-in flow has built-in CSRF protection, but the ~50 other
  mutating routes (all cookie-session-authenticated) didn't have an
  explicit check beyond `SameSite=Lax`'s own partial mitigation.
- Explicit session cookie configuration (`HttpOnly`, `Secure`,
  `SameSite=Lax`) — previously relying on Auth.js v5's defaults, which
  are correct but unverified by any test; now explicit and tested.
- A dependency audit (`pnpm audit`) with each finding triaged.
- The real backup/restore mechanism — `docker/backup/backup.sh` was
  still M00's placeholder ("TODO(M01): once prisma/schema.prisma
  exists, replace the echo below with a real pg_dump" — never done).

## Scope decisions this module makes

- **BR-03/BR-05 stay computed, never stored or auto-acted-on** —
  consistent with every other "eligibility-shaped" rule in this build
  (BR-01, BR-04, BR-27's SLA breach). A stored `graduationEligible`
  column or an automatic `CLOSED_INCOMPLETE` transition on a missed
  deadline would both contradict their own rule text ("flagged, not
  auto-failed"; BR-04's "read-only... no API route may write to it").
- **CSRF via Origin validation, not per-request tokens.** A double-
  submit-cookie or synchronizer-token scheme is the more traditional
  defense, but this is a same-origin, cookie-session API with no
  cross-origin fetch surface by design (§6.3: no CDN, no client-side-
  only authorization) — validating `Origin`/`Referer` against the
  configured `APP_URL` on every mutating request is the standard modern
  defense for exactly this shape of application and needs no per-form
  token plumbing through every one of the ~50 existing mutating routes.
- **`style-src 'unsafe-inline'`, `script-src` strict (nonce-based).**
  No component in this codebase uses an inline `style` attribute
  (checked directly), but Next's own font-optimization and hydration
  machinery can still emit inline `<style>`; relaxing only `style-src`
  — never `script-src`, where injection is the actually dangerous case
  — is the standard, documented trade-off for a Next.js CSP.
- **The runbook and admin guide are new top-level docs**
  (`docs/RUNBOOK.md`, `docs/ADMIN_GUIDE.md`), not folded into
  `docs/ARCHITECTURE.md` — different audiences (an operator restoring a
  backup at 2am vs. a Focal Person's day-to-day use), different
  lifecycles.

## Done when

Every BR-01 to BR-28 has a passing named test (BR-03/BR-05 close the
last two gaps). `docs/SECURITY_CHECKLIST.md` demonstrates every §9 item
live, cross-referenced to a real test or a real, run command. A backup
taken from one Postgres instance restores into a completely empty one
and the restored data matches exactly (proved with a live script, not
asserted). `docs/RUNBOOK.md` covers deploy, roster import, semester
open/close, backup/restore, and adding a user without needing anything
beyond itself.

## Additional gaps found during implementation (not anticipated above)

Two more real gaps surfaced only once implementation and — critically —
real `docker compose up --build` verification actually started; neither
was visible from reading the code or the master prompt alone:

- **`users.manage` existed since M02 with no route behind half of what
  its own name promises.** It already gated roster import and
  semester routes, and §2.6/§3 both explicitly name "create and
  deactivate user accounts" as an Admin capability — but no module
  ever built that route, meaning there was genuinely no way to
  onboard a new Focal Person, exactly what this module's own §8.3
  runbook requirement needs to cover. Fixed: `POST /api/admin/users`
  / `POST /api/admin/users/:id/deactivate` (see
  `src/server/users/service.ts` and `docs/DECISIONS.md` D-097).
- **The backup/restore mechanism, as first built this module, didn't
  actually work** — three separate, real bugs, each found only by
  doing the literal thing this module's own done-criterion demands
  (a real restore rehearsal against a real, separate database), not
  by code review or the test suite: a permission error on every
  scheduled dump from first container start (a fresh named Docker
  volume defaults to root ownership; nothing created `/backups` in
  the image), invisible in `docker compose ps` because the old
  healthcheck only proved the loop was alive; `pg_dump`/`pg_restore`
  rejecting Prisma's own `?schema=public` connection-string
  parameter outright; and — the most serious of the three —
  `pg_restore --clean` silently re-widening BR-26's append-only
  revokes on `audit_events`/`case_events`/`grades` by re-triggering a
  standing default-privileges rule when those tables get dropped and
  recreated. All three fixed and re-verified against a real restored
  database; see `docs/DECISIONS.md` D-098 through D-100 for the full
  account of each.
