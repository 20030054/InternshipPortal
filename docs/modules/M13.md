# M13 — Dashboards and reporting

## Purpose

The first UI module. Every module through M12 shipped an API surface
with no screen behind it — M00's placeholder home page and M02's
deliberately unstyled login page both say so explicitly ("replaced
entirely by M13"). This module builds the four real screens
§1.1/§10/§7 describe (student progress line, Focal work queue, HoD
department view, Dean read-only view) and the two export formats
(XLSX, PDF), on top of the design system M00 already scaffolded
(`tailwind.config.ts`, `globals.css`'s palette, `components.json`).

**Depends on:** every prior module for the data it renders. M12's
`workingDaysElapsed()`/`isFocalSlaBreached()`, reused (not
reimplemented) for the Focal queue's own sort order.

## Scope decisions this module makes

- **Views and exports, not action-taking forms.** The module summary
  line describes screens and exports, not workflow UI — every mutating
  action (approve/reject an offer, verify a deliverable, countersign a
  restart, rule on a waiver...) already has a real, tested API route
  from M05 through M11. Building a written-reason-in-a-dialog form for
  each of them (§10's own requirement, once that UI exists) is a
  large, separable piece of work this module's own "done when" — "the
  HoD can answer 'who is at risk of not graduating' in one screen" —
  doesn't need. Every dashboard here is read-only; taking action still
  means calling the existing API directly. A natural, additive
  follow-on, not a gap in this module.
- **Hand-built UI primitives, not the shadcn CLI.** `components.json`
  already configures shadcn/ui's conventions (aliases, CSS variables,
  Tailwind integration) — but the CLI itself fetches component source
  from a registry at generation time, and only Button, Badge and Card
  are actually needed this session. Hand-writing these three against
  the same conventions (`cva` for variants, `cn()` merging, the exact
  aliases `components.json` already declares) produces the identical
  shape the CLI would, without the extra moving part.
- **`overdue eligibility` reads as "eligible, zero cases, hasn't acted"**
  — the same candidate population BR-02's sweep watches
  (`cases: none`), but reported here rather than acted on, filtered to
  `computeEligibility(...).isEligible` rather than
  `isPastAutoEnrollBoundary`. A student who's been eligible for two
  semesters and never opened a case is exactly "at risk of not
  graduating" in the done-criterion's own words — the earliest, most
  actionable signal the HoD can see, well before BR-02's semester-6
  fallback would auto-enroll them anyway.
- **The Dean's view is the same aggregate data as the HoD's, framed
  read-only, plus what's specifically waiting on the Dean** (waivers at
  `WAIVER_COUNTERSIGNED`, denied restarts not yet ruled on). No new
  capability — `case.view_any` already includes `DEAN` (M02's matrix).
  Nothing about being "read-only" needed enforcing here beyond simply
  not rendering action buttons; the Dean already can't call any
  mutating route this build doesn't already gate by role.
- **One PDF artefact this session: the case summary.** §10 lists three
  printed artefacts (case summary, supervisor evaluation, annual
  report). The case summary is the one every other module's data
  already fully supports end to end (case, offer, deliverables,
  verification, grade) and the one the done-criterion's "one screen"
  test most directly implies backing up with a document. The
  supervisor-evaluation PDF and department annual report are real,
  useful, and out of scope for this session — both are additive (same
  `@react-pdf/renderer` machinery, different query), not a rewrite.
- **XLSX export covers the HoD department view's own data** (counts by
  state, overdue eligibility, pending verifications, waivers,
  restarts) — the one export the done-criterion's own scenario would
  actually need to hand to someone who isn't looking at the screen.
- **`exceljs` for XLSX** — `MASTER_PROMPT.md` §6.1 doesn't name an XLSX
  library (only PDF: `@react-pdf/renderer`). `exceljs` is actively
  maintained and has no history of the parsing-side CVEs the more
  common `xlsx`/SheetJS package has carried; this build only ever
  *writes* spreadsheets, but "well-maintained, no CVE history" is a
  reasonable bar for a new dependency regardless.

## Screens

- **`/`** — role-dispatching. `STUDENT` renders the progress line
  inline (§10: "the student's entire home page"); `FOCAL`/`HOD`/`DEAN`
  redirect to their own screen; unauthenticated redirects to `/login`.
- **`/focal`** — the work queue: every case in `OFFER_UNDER_REVIEW` or
  `PENDING_VERIFICATION`, sorted by SLA risk (most overdue first, not
  by date — §10's own requirement), each row showing current state,
  who's responsible next (always the Focal Person, by construction —
  these are exactly the two states M12 tracks as Focal-pending), and
  the deadline.
- **`/hod`** — counts by state, the overdue-eligibility list, pending
  verifications, every waiver (BR-24), every restart request. An XLSX
  export link.
- **`/dean`** — the same aggregate data, read-only framing, plus
  what's specifically awaiting the Dean.

## Business rules enforced

- **BR-24** (again) — "every waiver is surfaced permanently on the HoD
  dashboard" — this is the module that finally puts M11's
  `listWaivers()` somewhere a human looks at it.
- The eight-step table (§1.1) is the literal data the progress line
  renders — `computeProgressLine()` is a pure function of `CaseState`,
  unit-tested against the full state enum including the three
  exception paths (restart/waiver/withdrawal), which aren't numbered
  steps and render distinctly.

## Done when

The HoD can answer "who is at risk of not graduating" in one screen —
`/hod` surfaces the overdue-eligibility list and the SLA-breached
cases (via the same computation M12's escalation sweep uses) together,
without navigating elsewhere. Every new pure function
(`computeProgressLine()`, the SLA-risk sort) has unit tests including
every `CaseState` and boundary/edge cases; every dashboard query has an
integration test proving role-gating (a Student can't load `/hod`, a
Focal Person's queue never includes another Focal Person's
unrelated states) and correct aggregation against real fixture data.
