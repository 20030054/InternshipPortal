# M06 — Document vault

## Purpose

Harden the interim upload writer M05 built out of necessity
(`src/server/documents/store.ts`) into the real thing: magic-byte
sniffing, an actual ClamAV scan, and — the half M05 explicitly deferred
— an authenticated streaming download route that checks capability and
logs every access. Also closes a real gap M05 left open: nothing marked
a prior document `SUPERSEDED` when a new one replaced it, so a
resubmitted offer letter left two `ACTIVE` rows behind.

**Depends on:** M01 (`documents`/`DocumentStatus`, the
SUPERSEDED-can't-reactivate trigger), M02 (`requireCapability`,
`case.view_own`/`case.view_any`), M05 (`storeDocument()`, the case
ownership pattern its routes established).

## Scope decisions this module makes

- **The completion-certificate upload route is in scope; the "all three
  deliverables" gate (BR-10) mostly isn't.** `document.upload_
  completion_certificate` (M02) has had no route since the capability
  matrix was built — a plain, non-transition-gated upload is a natural,
  low-risk exercise of the hardened writer, and M09 (verification) needs
  `COMPLETION_CERTIFICATE` `Document` rows to exist before it can verify
  them. But BR-10 ("cannot enter `PENDING_VERIFICATION` until all three
  deliverables exist: offer letter, completion certificate, supervisor
  evaluation") needs a *third* leg — the supervisor evaluation — that has
  no data model at all yet (`DocumentType` has no `SUPERVISOR_EVALUATION`
  variant; M08's tokenised form submission almost certainly won't be a
  `Document` row the way file uploads are). Row 9's guard
  (`DOCS_PENDING → PENDING_VERIFICATION`) stays `stubGuard("BR-10")` —
  wiring two of three legs for real would still leave the transition
  permanently unreachable in practice (no code path can ever supply the
  third leg's `true` until M08 exists), which would make row 9's own
  success-path test synthetic rather than real. The stub's comment is
  updated to name both M08 and M09, not just M09.
- **The completion-certificate upload triggers no transition.** Row 8
  (`IN_PROGRESS → DOCS_PENDING`, STUDENT, no guard) already lets a
  student move to `DOCS_PENDING` at will — nothing ties it to document
  existence today, and `MASTER_PROMPT.md` doesn't say uploading the
  certificate should auto-advance the case. M07 (progress tracker) reads
  as the module that actually owns *when* a case should move to
  `DOCS_PENDING` (it's the one tracking weeks completed and the
  actual-vs-planned dates); guessing at that logic here would risk
  redoing it. The completion-certificate route only ever creates a
  `Document` row.
- **Supersede-on-reupload applies per `(caseId, type)`, uniformly across
  all three `DocumentType` values, not just the two "single current
  deliverable" ones.** `OFFER_LETTER`/`COMPLETION_CERTIFICATE` clearly
  want "one current file, prior ones superseded, never deleted."
  `SUPPORTING_EVIDENCE`'s eventual semantics (attached by the restart
  gate, M10, not built yet) are genuinely unknown — it might turn out to
  want multiple concurrent active attachments. Applying the same rule
  uniformly for now is the restrictive default (fewer concurrently
  "current" documents to reason about, not more); narrowing it to skip
  `SUPPORTING_EVIDENCE` later, if M10 needs that, is a small, additive
  change to one `where` clause, not a rewrite.
- **No new capability for downloads.** `MASTER_PROMPT.md` §3's eighteen
  rows have no "download document" row — §2.1's prose lists it as
  something a Student can do, but the enumerated capability table
  doesn't give it its own permission. The download route reuses
  `case.view_own`/`case.view_any` (the same capabilities the case GET
  route already uses): if an identity can see a case, it can see that
  case's documents. Inventing a new capability not in the master
  prompt's own table would be adding authority surface the spec didn't
  ask for.
- **ClamAV is mocked in the fast test suite, proven for real against the
  compose stack.** The temp Postgres/Redis containers this project's
  test loop already uses have no ClamAV alongside them (its virus
  database load takes minutes on first boot — impractical for a fast
  dev loop), so `tests/integration/setup.ts` mocks
  `@/server/documents/clamav`'s `scanBuffer()` to report clean by
  default, the same boundary M02 already drew around `sendMail()`. The
  real clamd protocol client is exercised for real during this module's
  `docker compose` verification, including a genuine EICAR test string
  (the antivirus industry's standard, safe-by-design "this should be
  detected" file) to prove a real positive, not just a real negative.
- **A failed or unreachable scan rejects the upload — fails closed.**
  `MASTER_PROMPT.md` §9 states uploads are "scanned by ClamAV" as a plain
  fact about the system, not a best-effort nicety. If the `clamav`
  service is unreachable, the upload is rejected with a distinct error
  rather than silently accepted unscanned.

## Data touched

None. `documents`/`DocumentStatus` (M01) already have every column and
constraint this module needs — no migration.

## Business rules enforced

- **BR-07/BR-09 (defence in depth, indirectly)** — magic-byte and
  extension validation now sit alongside the MIME-allowlist check M05
  already had, so "the offer letter file" can't be satisfied by an
  arbitrary byte stream wearing a `application/pdf` label.
- **The Files requirements in `MASTER_PROMPT.md` §9**, taken directly:
  "validated by extension and magic bytes and MIME, scanned by ClamAV" —
  `storeDocument()` now does all four checks, in that order (cheapest
  first: size, then MIME label, then magic bytes, then extension, then
  the ClamAV round-trip last since it's the slowest). "No document is
  ever deletable; superseded documents are marked SUPERSEDED and
  retained" — the new supersede-on-reupload logic. "Downloads stream
  through an authenticated handler with `Content-Disposition: attachment`
  and `X-Content-Type-Options: nosniff`" — the new download route,
  literally.
- **BR-26 (the download/denial half)** — every successful download and
  every denied access attempt against a real document writes an
  `audit_events` row. This module only wires that up for its own
  routes (upload, download) — retrofitting audit-on-denial onto every
  other route in the app is a bigger, cross-cutting change better suited
  to M14's hardening pass, not guessed at here.

## API routes

| Method | Route | Capability | Notes |
|---|---|---|---|
| `POST` | `/api/cases/:id/completion-certificate` | `document.upload_completion_certificate` (STUDENT, owner only) | Case must be `IN_PROGRESS` or `DOCS_PENDING`. Supersedes any existing `ACTIVE` `COMPLETION_CERTIFICATE` for the case. |
| `GET` | `/api/documents/:id/download` | `case.view_own` / `case.view_any` (via the document's case) | Streams the file, `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`. 404 for a nonexistent id or one the caller doesn't own. Every attempt (success or denial against a real document) writes an `audit_events` row. |

## Test list

- `unit/magic-bytes.test.ts` — `sniffFileType()` recognises PDF/JPEG/PNG
  signatures and returns `null` for garbage bytes; `extensionMatches()`
  pairs each MIME with its expected extension(s) and rejects mismatches.
  No database, no network.
- `unit/clamav-protocol.test.ts` — `buildInstreamPayload()` (the pure
  byte-framing half of the clamd INSTREAM protocol) produces the correct
  length-prefixed chunk sequence, tested against known byte layouts. The
  actual `net.connect()` I/O is not unit-tested (see the real-ClamAV
  compose verification below).
- `integration/M06_upload_hardening.test.ts` — `storeDocument()` rejects
  a MIME/magic-byte mismatch, an unrecognised extension, and (with
  `scanBuffer` mocked to report infected) a flagged file; accepts a
  genuinely valid PDF.
- `integration/M06_document_supersede.test.ts` — re-uploading the same
  `(caseId, type)` marks the prior `ACTIVE` row `SUPERSEDED` and leaves
  it in place (never deleted); a second, different `type` for the same
  case is untouched.
- `integration/M06_completion_certificate_upload.test.ts` — the route's
  ownership pattern (404 for another student's case), the `IN_PROGRESS`/
  `DOCS_PENDING` state gate, and that no transition fires as a side
  effect.
- `integration/M06_document_download.test.ts` — the owning student and
  any Focal/HoD/Dean can download; another student gets 404; an
  unauthenticated request gets 401; a random UUID gets 404; a successful
  download and a denied one against a real document both write an
  `audit_events` row with the right `event_type`.

## Done criteria

1. A direct URL guess against the download route returns 404
   (`MASTER_PROMPT.md`'s own stated done criterion).
2. Every download — successful or denied against a real document —
   appears in `audit_events`.
3. A re-upload marks the prior document `SUPERSEDED`, never deletes it.
4. The real ClamAV scan is proven against the real `clamav` compose
   service, both a clean file and a genuine EICAR positive.
5. `docker compose up --build` succeeds from a clean volume state.
6. `/docs/PROGRESS.md` updated, M06 checked off.
