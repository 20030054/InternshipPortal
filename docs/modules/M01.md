# M01 — Data model and migrations

## Purpose

Establish the entire database schema, its constraints, its two-role
privilege separation, the audit table, and the state-write trigger, before
any business logic exists. Per `PROJECT_DOCUMENTATION.md` §4.2 (three
enforcement layers), the database is the *first* and most authoritative
layer — a rule expressible as a constraint must be one here, not deferred
to a service that a future bug could bypass.

**Depends on:** M00 (needs a running Postgres container and migration
tooling wired up).

**Blocks on:** OQ-10 (SCIT-only vs. shared BNU tenancy) affects whether
`students`/`cases`/etc. need a `school_id`/tenant column from day one.
Adding a tenancy column later is a straightforward migration (nullable,
backfilled, then constrained); retrofitting it under load is not. Absent an
answer, implement the **most restrictive** reading per §0.2: build the
schema SCIT-only (no tenant column), but keep entity boundaries clean
(no cross-cutting lookups by anything other than explicit foreign keys) so
a tenancy column can be added later without a structural rewrite. Mark the
decision `TODO(OQ-10)` in `prisma/schema.prisma` as a comment above
`Student` and `User`.

## Data touched

Everything. This module *is* the data model. Entity list and purpose, from
`PROJECT_DOCUMENTATION.md` §7.1:

`users`, `roles` / `user_roles`, `students`, `semesters`, `cases`,
`case_events`, `companies`, `documents`, `verifications`, `grades`,
`grade_reversals`, `supervisor_tokens`, `evaluations`, `restart_requests`,
`waivers`, `escalations`, `audit_events`, `notifications`.

### Key columns and constraints, table by table

**`users`** — `id` (uuid v7, pk), `email` (unique, citext), `password_hash`
(nullable — null if the account will only ever authenticate via future
OIDC), `created_at`, `disabled_at` (nullable; Admin deactivates, never
deletes a user).

**`roles`** — fixed lookup: `STUDENT`, `FOCAL`, `HOD`, `DEAN`, `ADMIN`.
Seeded, not user-editable.

**`user_roles`** — `user_id`, `role_id`, composite pk. A user may hold
multiple roles (§2 of `MASTER_PROMPT.md`); separation-of-duty is enforced
per case at the service layer (BR-12), not by restricting role
combinations here.

**`students`** — `id` (uuid v7, pk), `user_id` (fk, unique — one student
account per user), `registration_number` (unique), `admission_semester_id`
(fk -> `semesters`), `programme`. `registration_number` unique constraint
is the anti-duplicate-enrolment control at the data layer.

**`semesters`** — `id`, `type` (`FALL`/`SPRING`/`SUMMER`), `year`,
`starts_on`, `ends_on`, `document_deadline` (nullable until OQ-01 answers
per-semester dates — see `TODO(OQ-01)`), unique on `(type, year)`.

**`cases`** — `id` (uuid v7, pk), `student_id` (fk), `state` (text,
constrained by a `CHECK` against the fixed state list in
`MASTER_PROMPT.md` §5.1), `previous_case_id` (nullable, self-referencing fk
— the restart link, BR-20), `company_id` (nullable fk, set once an offer
is submitted), `planned_start`/`planned_end`/`actual_start`/`actual_end`
(BR-08 variance tracking), `created_at`, `updated_at`.
- **Partial unique index**: `UNIQUE (student_id) WHERE state NOT IN
  (<terminal states>)` — this is BR-06 (at most one non-terminal case per
  student) enforced as a constraint, not application logic. Terminal
  states per `PROJECT_DOCUMENTATION.md` §4.5: `CLOSED_PASS`,
  `CLOSED_INCOMPLETE`, `WITHDRAWN`, `WAIVER_GRANTED`, `WAIVER_DENIED`,
  `RESTART_DENIED`. (`RESTART_DENIED` is terminal *for the request*, not
  the student per §5.1 — the student's case itself moves on via escalation
  or stays `CLOSED_INCOMPLETE`; either way it is excluded from "one
  non-terminal case" because the case row itself isn't open.)
- `state` column has a database trigger (see below) rejecting any
  `UPDATE` that didn't originate from the transition executor's tagged
  transaction.

**`case_events`** — `id`, `case_id` (fk), `actor_user_id` (nullable —
null + `system_job` populated means a `SYSTEM` actor), `from_state`,
`to_state`, `reason` (nullable, required by app logic when
`requiresReason`), `created_at`. Append-only: no `UPDATE`/`DELETE`
application privilege (same pattern as `audit_events`, see below) — this
*is* the audit trail for state, distinct from the general `audit_events`
table which covers everything else (uploads, downloads, denials).

**`companies`** — `id`, `name`, `normalised_name` (generated/stored,
lower-cased and whitespace-collapsed — the input to BR-16 G1's match
check), `registration_number` (nullable, NTN or equivalent), `contact`.

**`documents`** — `id`, `case_id` (fk), `type`
(`OFFER_LETTER`/`COMPLETION_CERTIFICATE`/`SUPPORTING_EVIDENCE`/...),
`storage_key` (the UUID filename in the volume — never the original
name), `original_filename` (metadata only, never used to build a path),
`checksum_sha256`, `status` (`ACTIVE`/`SUPERSEDED`), `uploaded_by`,
`created_at`. No delete privilege for the app role; `status` transitions
`ACTIVE -> SUPERSEDED` only, enforced by a trigger that rejects the reverse
(a CHECK can't see the row's previous value, so a trigger — not a CHECK —
is the correct mechanism here; see DECISIONS.md D-011).

**`verifications`** — `id`, `document_id` (fk), `method` (`CHECK`
constrained to the fixed list in BR-11), `verifier_user_id`, `note`
(nullable), `created_at`.

**`grades`** — `id`, `case_id` (fk, unique — one grade row per case,
ever), `value` (`CHECK IN ('P','I')`), `recommended_by`, `awarded_by`,
`created_at`. `CHECK (recommended_by <> awarded_by)` at the database level
as a second line of defence for BR-12, in addition to the service-layer
check (defence in depth — the spec calls this out as "compare user IDs,
not role names," which is a service-layer instruction, but the constraint
costs nothing extra and catches a bug the service layer might not). No
`UPDATE`/`DELETE` app privilege — immutability (BR-14) enforced at the
grant level, not just by omitting an update route.

**`grade_reversals`** — `id`, `grade_id` (fk), `reason`,
`dean_user_id`, `created_at`. Additive only; the original `grades` row is
never touched.

**`supervisor_tokens`** — `id`, `case_id` (fk), `token_hash` (the raw
token is never stored — only its hash, per §9 "Sessions and secrets"),
`expires_at`, `used_at` (nullable; set once, `CHECK` prevents reuse logic
relying solely on app code — a partial unique index on `case_id WHERE
used_at IS NULL` limits to one *live* token per case, replacements
explicitly revoke the prior one first), `revoked_at` (nullable).

**`evaluations`** — `id`, `supervisor_token_id` (fk, unique — one
evaluation per token, structurally preventing replay at the schema level
in addition to the app-level lock), `content` (jsonb or discrete columns
per the eventual form spec — decided in M08), `created_at`.

**`restart_requests`** — `id`, `failed_case_id` (fk -> cases),
`new_company_id` (fk), `g1_result`/`g2_result` (jsonb guard results, for
audit legibility), `focal_signer_id`, `focal_reason`, `focal_signed_at`,
`hod_signer_id` (nullable until countersigned), `hod_reason`,
`hod_signed_at`, `outcome`
(`PENDING`/`AUTHORIZED`/`DENIED`), `restart_cap_at_request` (snapshot of
the config value used, so a later config change doesn't rewrite history).
`CHECK (focal_signer_id <> hod_signer_id)` — BR-17 G3/G5 defence in depth.

**`waivers`** — `id`, `student_id` (fk, **unique** — BR-23 "at most one
waiver per student, ever" as a hard constraint), `circumstance` (text,
app-layer enforces ≥300 chars, a `CHECK (char_length(circumstance) >=
300)` adds a second line of defence), `focal_signer_id`/`focal_reason`,
`hod_signer_id`/`hod_reason`, `dean_signer_id`/`dean_reason`, `outcome`
(`PENDING`/`GRANTED`/`DENIED`), timestamps for each signature.

**`escalations`** — `id`, `subject_type`
(`RESTART_DENIED`/... — extensible but only one value exists at launch),
`subject_id`, `dean_user_id`, `reason`, `ruling`, `created_at`. Final —
no further transition consumes an escalation row.

**`audit_events`** — `id`, `actor_user_id` (nullable for `SYSTEM`),
`system_job` (nullable, populated when actor is null), `event_type`,
`entity_type`, `entity_id`, `metadata` (jsonb — never document contents,
tokens, or passwords, per §9 Privacy), `created_at`. **This is the table
the runtime database role has `INSERT`+`SELECT` on and explicitly not
`UPDATE`/`DELETE`.** Append-only at the privilege level, not just by
convention — this is the concrete implementation of BR-26.

**`notifications`** — `id`, `template_id`, `template_version`,
`recipient`, `sent_at` (nullable until actually sent), `status`
(`QUEUED`/`SENT`/`FAILED`), `case_id` (nullable fk, for correlation).

## Business rules enforced

Every rule in `MASTER_PROMPT.md` §4 that can be expressed as a database
constraint, per M01's done criterion. Explicitly, at the schema level in
this module:

- **BR-06** — partial unique index on `cases(student_id)` for non-terminal
  states.
- **BR-07** — `CHECK (char_length(work_description) >= 200)` once the
  offer-letter fields land on `cases` (or a dedicated `offers` extension —
  decide in M05; the column-level check belongs wherever the field lives).
- **BR-13** — `CHECK (value IN ('P','I'))` on `grades`.
- **BR-14** — immutability via revoked `UPDATE`/`DELETE` grants on
  `grades` for the runtime role.
- **BR-17 (G3/G5 partial)** — `CHECK (focal_signer_id <> hod_signer_id)`
  on `restart_requests`.
- **BR-19** — `restart_cap_at_request` snapshot column (the cap check
  itself is a service-layer count comparison; the schema just makes sure
  history isn't silently reinterpreted by a later config change).
- **BR-20** — `previous_case_id` self-referencing fk, nullable, never
  updated once set (no update grant needed since it's set at insert).
- **BR-23** — unique constraint on `waivers(student_id)`.
- **BR-25** — the `cases.state` write-trigger (below).
- **BR-26** — revoked `UPDATE`/`DELETE` on `audit_events` and
  `case_events` for the runtime role.

## The state-write trigger

A `BEFORE UPDATE OF state ON cases` trigger that rejects the update unless
a session-local flag (set only inside the transition executor's
transaction, e.g. via `SET LOCAL app.transition_authorized = 'true'`
immediately before the `UPDATE`, reset by transaction end) is present.
Direct `UPDATE cases SET state = ...` from `psql` or any other code path
fails. This is the concrete mechanism behind "the transition executor is
the only code path permitted to write `cases.state`" (§5.2) — M04 builds
the executor that sets the flag; M01's job is to build the trigger that
requires it, and prove the negative (a raw `UPDATE` fails) before M04
exists to prove the positive.

## Two database roles

- **Migration role** (`DATABASE_MIGRATION_ROLE`) — owns the schema, runs
  `prisma migrate deploy`. Used only during deploy, never by the running
  app.
- **Runtime role** (`DATABASE_APP_ROLE`) — what `app`/`worker` connect as.
  Grants: full `INSERT`/`SELECT`/`UPDATE`/`DELETE` on ordinary tables,
  **`INSERT`+`SELECT` only** on `audit_events` and `case_events`, **no
  `UPDATE`/`DELETE`** on `grades` (insert-only; reversal is a separate
  insert into `grade_reversals`), no DDL rights at all.

The init migration itself creates the role and applies these grants (not
the seed script — see DECISIONS.md D-012: a production deploy runs
`prisma migrate deploy` but has no reason to ever run `prisma db seed`, so
privilege restrictions living only in the seed script would silently not
apply in production). A test in M01 proves the runtime role cannot
`UPDATE`/`DELETE` the restricted tables (this is also demonstrated live
again at M14, but the automated test belongs here, at the point the
constraint is created).

## Seed script

`prisma/seed.ts`: the five roles, a test roster (~15–20 students spread
across semesters 3–8, per `MASTER_PROMPT.md` §11 seed-data guidance — the
full richly-populated demo dataset with cases in every state is more
naturally M13's job once there's a UI to see it in, but a *minimal* seed
here — roles, a handful of students, one semester — is what M01's own
tests need to run without M13 existing yet).

## Test list

- `schema.test.ts` — migration applies cleanly to an empty database.
- `BR06_one_nonterminal_case_per_student.test.ts` — inserting a second
  non-terminal case for the same student violates the partial unique
  index; inserting a second *terminal* case does not.
- `BR13_grade_value_constrained.test.ts` — inserting a grade with a value
  other than `P`/`I` is rejected.
- `BR14_grades_immutable.test.ts` — runtime role `UPDATE`/`DELETE` on
  `grades` fails with a permission error.
- `BR23_one_waiver_per_student.test.ts` — second waiver insert for the
  same student violates the unique constraint.
- `BR25_state_write_trigger.test.ts` — a raw `UPDATE cases SET state =
  ...` outside the authorized-transaction flag fails; the same statement
  inside a transaction that sets the local flag succeeds.
- `BR26_audit_append_only.test.ts` — runtime role `UPDATE`/`DELETE` on
  `audit_events` and `case_events` fails with a permission error.
- `seed.test.ts` — seed script runs idempotently (running it twice doesn't
  duplicate roles or error).

## Done criteria

1. Every table above exists via a versioned Prisma migration, applied by
   the migration role.
2. Every business rule listed under "Business rules enforced" above has a
   passing constraint-level test proving both that valid data is accepted
   and invalid data is rejected.
3. The runtime role's restricted grants are proven by test (not just
   asserted in a comment).
4. Seed script populates roles + a minimal test roster and runs
   idempotently.
5. `docker compose up --build` still succeeds from a clean volume state
   (M00's criterion still holds with the schema now present).
6. `/docs/PROGRESS.md` updated, M01 checked off.
7. `TODO(OQ-10)` comment present in `schema.prisma` at `User` and
   `Student` marking the tenancy question as unresolved and the chosen
   restrictive interpretation.
