# M04 — Case lifecycle core

## Purpose

Build the one mechanism every later module (M05 through M11) drives
instead of writing `cases.state` directly: a declarative transition
table, a single executor that is the only code path permitted to invoke
the M01 trigger's authorized-write flag, a pure-function guard
framework, and case-event/audit-event emission. No UI, no routes beyond
what M04's own tests need.

**Depends on:** M01 (schema, the `cases_state_write_guard` trigger, the
`case_events`/`audit_events` tables), M03 (semester/eligibility data the
restart guards read).

## Scope decisions this module makes

- **Division of labour with M05/M09/M10:** `MASTER_PROMPT.md` §7 gives
  M10 "the four guards" for the restart gate and M09 the verification/
  grading guards as their own deliverables. M04 still implements the
  restart guards (G1/G2/G4/G5) for real — the supporting data
  (`Company`, `RestartRequest`, `RESTART_CAP`, M03's eligibility
  machinery) already exists, and §5.3 specifies them precisely enough to
  implement correctly now. M10's remaining work is the *workflow* around
  them (routes, dual-session sign-off, Dean escalation), reusing these
  guards rather than reimplementing them. By contrast, BR-07/08/09/10/11
  guards (offer completeness, duration, relevance, deliverable presence,
  verification) stay as clearly-marked stub functions that always pass —
  the fields those checks need (offer letter data on `cases`, for
  instance) don't exist yet per M01's explicit deferral to M05. M05/M09
  replace the stub with a real guard function; the table and executor
  never change shape when they do.
- **`ELIGIBILITY_PENDING` → `ELIGIBLE` is a defined transition with no
  current caller.** Per OQ-11 (raised in M03), no code path today creates
  a case sitting in `ELIGIBILITY_PENDING` — the normal path's first case
  row is born already `OFFER_SUBMITTED` or later (M05, student action),
  and BR-02's fallback is born already `ELIGIBLE` (M03). The transition
  is still declared, tested against a synthetic fixture, and available if
  a future module or a revised OQ-11 answer needs it. Its guard checks
  BR-01 via `computeEligibility()` from M03.
- **New question, OQ-12 — do the `WAIVER_*` `CaseState` values represent
  real `cases.state` transitions?** M01's schema gave `Waiver` no
  `case_id` at all — it's keyed to `student_id` directly, tracked
  entirely through its own `outcome` field (`PENDING`/`GRANTED`/
  `DENIED`), independent of any Case row. BR-21 ("the only route that
  skips the eight steps entirely") reads as consistent with that: a
  waiver doesn't require a case to exist. Restrictive interpretation
  applied: `WAIVER_REQUESTED`/`WAIVER_COUNTERSIGNED`/`WAIVER_GRANTED`/
  `WAIVER_DENIED` are **not** used as `cases.state` transition targets in
  this module's table — the waiver workflow (M11) is driven entirely
  through the `waivers` table, which M01 already built for exactly this.
  These four enum values stay in `CaseState` (removing them would be a
  breaking schema change for no benefit) but M04's transition table has
  no entry that produces them. Logged in `OPEN_QUESTIONS.md`; M11 should
  confirm this reading holds before building the waiver routes.
- **A new migration corrects M01's BR-06 partial index.** Read closely,
  §5.3's restart gate has the *old, failed* case's own `state` progress
  `CLOSED_INCOMPLETE → RESTART_REQUESTED → RESTART_AUTHORIZED`, at which
  point "(system) creates new case in `ELIGIBLE`" — a **second**, new
  Case row for the same student. M01's terminal-states list for the
  `cases_one_nonterminal_per_student` partial index
  (`CLOSED_PASS, CLOSED_INCOMPLETE, WITHDRAWN, WAIVER_GRANTED,
  WAIVER_DENIED, RESTART_DENIED`) didn't include `RESTART_AUTHORIZED` —
  meaning the old case, sitting in `RESTART_AUTHORIZED`, would still
  count as "non-terminal" and collide with the new `ELIGIBLE` case the
  moment it's created, violating BR-06 by the letter of M01's own
  constraint. `RESTART_AUTHORIZED` is added to the terminal set in this
  module's migration — the old case's story is over once a new one has
  spawned from it, even though its `state` column reads
  `RESTART_AUTHORIZED` rather than one of the original six literal
  values. BR-20 ("the failed case remains `CLOSED_INCOMPLETE` forever")
  is read as describing the immutable *academic record* (the grade row,
  which BR-14 already makes immutable, and the `case_events` audit
  trail — both permanently show the Incomplete outcome) rather than a
  literal promise that the `state` column's string value never advances
  past `CLOSED_INCOMPLETE`.

## Data touched

One migration on the existing schema:

- **`cases_one_nonterminal_per_student`** (M01's partial unique index on
  `cases`) is dropped and recreated with `RESTART_AUTHORIZED` added to
  the `WHERE state NOT IN (...)` exclusion list. Same mechanism, corrected
  list — see "Scope decisions" above.

No other schema changes. `case_events` and `audit_events` (M01) are
exactly what event emission writes to; nothing new is needed there.

## Business rules enforced

- **BR-25** — "every state transition is validated against an explicit
  allowed-transitions table... an unknown transition is a hard error,
  never a silent no-op." This is the module's entire reason to exist:
  `executeTransition()` looks up `(from, to)` in the table and throws
  `IllegalTransitionError` if no entry matches, before touching the
  database at all.
- **BR-26** — every transition attempt (successful or denied) writes an
  `audit_events` row; every successful transition also writes a
  `case_events` row. A guard failure is itself an audited event
  (`MASTER_PROMPT.md` §5.2: "A failed guard produces a structured denial
  that is itself audited").
- **BR-16 to BR-20 (partial)** — the restart gate's structural rules
  (reachable only from `CLOSED_INCOMPLETE`; a new linked case via
  `previousCaseId`; the failed case's history preserved) are enforced by
  the transition table's shape and the guards below. The *cap* (BR-19)
  and *dual-session, distinct-account* requirements (G3/G5) are enforced
  here at the guard level; the workflow around collecting two signatures
  from two separate sessions is M10's.
- **BR-12 (partial)** — `recommendedBy !== awardedBy` is checked as a
  transition guard on `GRADE_RECOMMENDED → CLOSED_PASS`/
  `CLOSED_INCOMPLETE`, in addition to M01's `grades_recommender_not_awarder`
  CHECK constraint (defence in depth, same pattern as always).

`executeSystemTransition()` entry point that takes a job name instead of

Withdrawal (#14–18) is only reachable before `APPROVED`, matching
`PROJECT_DOCUMENTATION.md` §4.4: "A student may withdraw a case before it
is approved." No transition from `APPROVED` onward reaches `WITHDRAWN`.

`RESTART_AUTHORIZED` has no further transition in this table — the "new
case in `ELIGIBLE` with `previousCaseId` set" that follows it is a fresh
`INSERT` on a **different** Case row (M10's job), not a transition of
this one. Same reasoning as M03's BR-02 sweep: genesis inserts don't need
the transition executor, only writes to an *existing* row's `state` do.

## Guard framework

```ts
type GuardResult = { ok: true } | { ok: false; reason: string };

// Pure: synchronous, no I/O, no database access. The executor gathers
// every field a guard might need before calling it — MASTER_PROMPT.md
// §5.2: "Guards are pure and unit-testable in isolation... No database
// writes inside a guard."
type GuardFn = (ctx: TransitionContext) => GuardResult;
```

`TransitionContext` is one shape covering every guard's needs (optional
`restart`/`grade` sub-objects populated only by callers that need them)
rather than a per-transition discriminated union — simpler to implement
and test, at the cost of guards being individually responsible for
checking their own required sub-object is present. Documented as a
deliberate simplicity-over-precision trade-off, not an oversight.

## API routes

None. M04 is executor + table + guards only, exercised by its own test
suite and by direct calls from later modules' route handlers — not by
any route of its own.

## Test list

- `unit/guards.test.ts` — every named guard function (BR-12 recommender/
  awarder, restart G1/G2/G4/G5) tested directly against plain context
  objects, both the pass and fail path, no database involved. Genuinely a
  unit test — guards are pure.
- `integration/M04_transition_executor.test.ts` — `executeTransition()`
  itself touches the database (case lookup, the `SET LOCAL`-gated update,
  event writes), so its own mechanics can't be a no-database unit test
  the way the guards can. Using small synthetic transitions (not the real
  table, via the executor's `table` override) against a real Postgres,
  proves: an undefined `(from, to)` pair throws `IllegalTransitionError`
  and leaves `state` provably unchanged in the database; the wrong actor
  role throws `WrongActorRoleError`; a transition marked `requiresReason`
  with no reason throws `MissingReasonError`; a failing guard throws
  `TransitionGuardError` and leaves `state` unchanged; a passing
  transition updates `state` and writes one `case_events` row (correct
  actor, from/to, reason) and one `audit_events` row; a `SYSTEM`-actor
  transition records `system_job` instead of `actor_user_id` on both; a
  denied transition's `audit_events` row records the denial reason too.
- `integration/M04_all_transitions.test.ts` — for each of the 21 real
  table rows, a case fixture seeded directly at the `from` state
  (bypassing the question of how it normally gets there) proves the
  transition succeeds under valid conditions and is rejected under each
  of its guards' failing conditions.
- `integration/BR06_restart_authorized_is_terminal.test.ts` — proves the
  M04 migration's fix: a case in `RESTART_AUTHORIZED` no longer blocks a
  new non-terminal case for the same student, where it would have under
  M01's original terminal-states list.

## Done criteria

1. Every one of the 21 transitions in the table has a passing test, both
   the success path and at least one failure path per guard it carries.
2. An undefined transition pair throws — proven by test, not just
   documented.
3. `cases.state` is provably unwritable by anything except
   `executeTransition()`/`executeSystemTransition()` — this was already
   true from M01's trigger; M04 proves its own code path is the only one
   that ever sets the `SET LOCAL` flag.
4. The `RESTART_AUTHORIZED` terminal-states fix is migrated and tested.
5. `docker compose up --build` succeeds from a clean volume state.
6. `/docs/PROGRESS.md` updated, M04 checked off.
