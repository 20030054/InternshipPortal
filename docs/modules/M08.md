# M08 — Supervisor evaluation

## Purpose

The one workflow in this system with an external, no-account actor:
signed, single-use, expiring tokens tied to one case, a public form
exposing only student name/company/dates, submission locking the token,
and a Focal-Person-issued replacement path. Gives BR-10's guard (`DOCS_
PENDING → PENDING_VERIFICATION`, still `stubGuard("BR-10")` since M06)
its third leg's data — though not the guard itself; see "Scope
decisions."

**Depends on:** M01 (`SupervisorToken`/`Evaluation`, the
`supervisor_tokens_one_live_per_case` partial index), M02
(`requireCapability`, `checkRateLimit`, the password-reset token
pattern this reuses almost line for line), M04 (row 9's stub this
doesn't touch), M06 (the "public, unauthenticated route" precedent —
this module's the second one, not the first).

## Scope decisions this module makes

- **A new `users.full_name` column — a real, previously-undiscovered
  schema gap, not an M08 invention.** `MASTER_PROMPT.md` §2.5 requires
  the public evaluation page to show "the student name" — but no
  `name`/`full_name` field exists anywhere in the schema; `User` only
  ever had `email`, `Student` only `registrationNumber`/`programme`.
  Nothing before M08 needed to display a human name anywhere. Added as
  `String?` (nullable, not backfilled) rather than blocking on a
  larger migration: existing test fixtures and any student imported
  before this column existed would otherwise need a rewrite far outside
  this module's scope. `src/server/roster/csv-import.ts` accepts an
  optional `fullName` column going forward (falls back to leaving it
  `null` if absent, consistent with OQ-06's already-loose roster
  format); the public evaluation page falls back to the student's
  `registrationNumber` if `fullName` is unset, so the page never renders
  broken, just less friendly.
- **The supervisor's email address is a parameter to the issue route,
  not read from anywhere already on the case.** `Company.contact`
  (M05) is a free-text field never validated as an email address and
  captured for a different purpose (the company's general contact,
  filled in by the *student* at offer time) — reusing it here would be
  guessing that it happens to be both an email and the right person's.
  The Focal Person supplies the supervisor's email explicitly when
  issuing (or replacing) a token; `SupervisorToken.supervisorEmail`
  (new column) records who each token was actually sent to, for audit
  and so a replacement's route handler doesn't need to guess it either.
- **The raw token is an HMAC digest, not bare random bytes; only its
  hash is stored — both halves of `MASTER_PROMPT.md` §9's "HMAC-signed
  ... and stored hashed" taken literally, not read as one property
  restated twice.** `rawToken = HMAC-SHA256(SESSION_SECRET,
  randomBytes(32))`; `tokenHash = SHA256(rawToken)` is what's persisted
  — the same "hash what's stored, keep the raw value out of the
  database entirely" shape `issuePasswordResetToken()` (M02) already
  established, extended with an HMAC layer over the random source so a
  compromised RNG alone (vanishingly unlikely with `node:crypto`, but
  the master prompt asks for the extra layer specifically for this
  token, not for password reset) isn't sufficient to forge one without
  also knowing the server secret.
- **BR-28's actual reminder emails and BullMQ schedule are M12's job;
  this module builds the detection and the token/audit trail they'll
  act on.** `MASTER_PROMPT.md` §7 gives M12 "BullMQ jobs for reminders
  ... the BR-28 supervisor escalation ... email templates ... versioned
  ... no ad-hoc strings" as its own explicit deliverables — a direct
  overlap with M08's own one-line summary naming "reminder schedule and
  the BR-28 non-response escalation." Building a real scheduled job and
  a second, ad-hoc email-templating scheme here would either duplicate
  M12's infrastructure before it exists or invent a throwaway version of
  it. `classifyTokenForReminder()` (pure, real, tested: given a token's
  age against `SUPERVISOR_SLA_DAYS` and how many reminders it's already
  recorded, returns none/first-reminder-due/second-reminder-due/
  escalate) and `recordReminderSent()` (real, callable, bumps the
  counter M12's future job will call) are this module's honest
  contribution — the token issuance email itself is sent by this module
  (a plain one-off function, same un-templated shape M02's password
  reset email used, since M12's "templated and versioned" system
  doesn't exist yet either), but the twice-reminded escalation flow
  itself stays unwired until M12 lands, exactly like M04 left BR-07/08/
  09/10/11 as named stubs for the modules that actually own them.
- **Evaluation visibility to the student is a config flag, defaulted
  hidden — `MASTER_PROMPT.md` says so explicitly (§9 "Privacy").**
  `SHOW_EVALUATION_TO_STUDENT` (new env var, default `false`). Read at
  the route boundary, not baked into a capability: Focal/HoD can always
  see it; a Student can only when the flag is on. Answers OQ-08 in the
  sense of implementing exactly what the master prompt already
  specified as the interim behaviour — the *question* (should the
  default ever change) stays open for the department.
- **Token issuance and replacement are the same operation, gated to
  `DOCS_PENDING`.** The eight-step table ties supervisor evaluation to
  step 6 (`DOCS_PENDING`, "Submit documents | Student + Supervisor") —
  issuing earlier would be issuing before the case has actually reached
  that step. "Focal Person can issue a replacement token" (§2.5) is the
  same code path as first issuance: the partial unique index (M01)
  already requires revoking any live token first, so "issue" always
  means "the live token for this case, if any, is now revoked, and this
  new one is live" — first-time issuance is just the case where there
  was nothing to revoke.

## Data touched

One migration on the existing schema:

- `users.full_name TEXT NULL` (new).
- `supervisor_tokens.supervisor_email TEXT NOT NULL` (new — every token
  from here on records who it was sent to; no existing rows to
  backfill, since no code path created any before this module).
- `supervisor_tokens.reminder_count INTEGER NOT NULL DEFAULT 0` and
  `supervisor_tokens.last_reminder_sent_at TIMESTAMPTZ NULL` (new —
  the state `classifyTokenForReminder()`/`recordReminderSent()` need;
  M12's future job is the only intended caller of the latter).

No changes to `SupervisorToken`'s existing columns, the
`supervisor_tokens_one_live_per_case` partial index, or `Evaluation` —
M01 already built exactly the shape this module needs for the
token/evaluation core.

## Business rules enforced

- **§2.5 (Industry Supervisor)** — the public GET route returns exactly
  student name (or registration number, see above), company name, and
  planned dates; nothing else. The public POST route accepts the
  evaluation once, locks the token, and a resubmission attempt (replay)
  is rejected with a distinct "already submitted" response rather than
  a generic error, matching this module's own stated done criterion.
- **§9 "Sessions and secrets"** — HMAC-signed, stored hashed, rate
  limited (`checkRateLimit`, same mechanism as login/password-reset).
- **§9 "Privacy" (OQ-08's interim answer)** — evaluation `content`
  visible to Focal/HoD unconditionally; to the Student only when
  `SHOW_EVALUATION_TO_STUDENT=true`.
- **BR-28 (the detection half)** — `classifyTokenForReminder()`,
  real and tested; the reminder-sending/escalation *action* is M12's.

## API routes

| Method | Route | Capability | Notes |
|---|---|---|---|
| `POST` | `/api/cases/:id/supervisor-token` | `supervisor_token.issue` (FOCAL) | Body: `supervisorEmail`. Case must be `DOCS_PENDING`. Revokes any live token first (audited either way — first issuance and replacement both write an `audit_events` row). |
| `GET` | `/api/supervisor/evaluate/:token` | none (public, no login) | Rate-limited. `404`-equivalent for invalid/expired/revoked; a distinct `already_submitted` body (not an error status) for a used token; only student name/company/dates otherwise. |
| `POST` | `/api/supervisor/evaluate/:token` | none (public, no login) | Rate-limited. Body: `performanceRating` (1-5), `comments`. Locks the token; a replay gets the same `already_submitted` response as the GET, not a 500 or a silent overwrite. |
| `GET` | `/api/cases/:id/evaluation` | `case.view_any` (FOCAL/HOD unconditionally) or `case.view_own` (STUDENT, only if `SHOW_EVALUATION_TO_STUDENT=true`) | `404` if no evaluation exists yet. |

`src/app/api/supervisor/**` is added to the mutating-route ESLint rule's
exclusion list alongside `src/app/api/auth/**` — both are
pre-authentication entry points with no identity to call
`requireCapability()` against; see `eslint.config.mjs`'s updated
comment.

## Test list

- `unit/supervisor-token-protocol.test.ts` — the HMAC-then-hash
  construction: same input never produces the same raw token twice
  (fresh randomness each call), the persisted hash is deterministic
  from a given raw token, tampering with one character of a raw token
  changes its hash. No I/O.
- `unit/reminder-classification.test.ts` — `classifyTokenForReminder()`
  against plain `{createdAt, reminderCount}` facts: none before the SLA
  window, first-reminder-due at the boundary, second-reminder-due after
  one reminder plus a further wait, escalate after two. No database.
- `integration/M08_supervisor_token_issue.test.ts` — capability/
  ownership are irrelevant to the *public* half but very much apply to
  issuance: FOCAL-only, case must be `DOCS_PENDING`, a second issuance
  revokes the first (proven against the DB row, not just the return
  value) and is itself audited.
- `integration/M08_supervisor_evaluation_flow.test.ts` — the full public
  flow: GET returns exactly the three allowed fields for a live token;
  an invalid/expired/revoked token gets a generic rejection; POST
  succeeds once, locks the token, and both a repeated GET and a repeated
  POST against the same token return the distinct `already_submitted`
  shape, not a generic error (this module's own stated done criterion).
  Rate limiting on the POST route is exercised directly.
- `integration/M08_evaluation_visibility.test.ts` — Focal/HoD see the
  evaluation regardless of the flag; a Student is rejected with the flag
  off and succeeds with it on (toggled via `process.env` within the
  test, not by reading a real deployment's value).

## Done criteria

1. A used token returns a clean "already submitted" page/response, and
   a replayed token is rejected — `MASTER_PROMPT.md`'s own stated done
   criterion for this module, proven for both the GET and the POST.
2. The public route exposes nothing beyond student name (or
   registration number), company name, and dates.
3. A replacement token is issued only by the Focal Person, is audited,
   and provably revokes the prior live token (the partial index would
   catch a bug here regardless, but the test proves the *service*
   revokes it, not just that a bug happens to be caught).
4. `docker compose up --build` succeeds from a clean volume state.
5. `/docs/PROGRESS.md` updated, M08 checked off.
