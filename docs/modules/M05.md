# M05 — Offer submission and approval

## Purpose

Give the normal path its first real caller: a student opens a case, submits
an offer letter, a Focal Person approves or rejects it with a mandatory
reason, and a rejected offer can be resubmitted. Replaces four of M04's
stub guards (BR-01, BR-07, BR-08, BR-09) with real ones, and is the first
module to call `executeTransition()`/`executeSystemTransition()` from an
actual route handler instead of a test.

**Depends on:** M02 (`requireCapability`, `getCurrentIdentity`), M03
(`computeEligibility()`), M04 (the transition table and executor).

## Scope decisions this module makes

- **Where the offer fields live.** M01 deferred this explicitly (see its
  comment on `model Case`). Two new nullable columns go directly on
  `cases` — `work_description` and `relevance_confirmed` — rather than a
  dedicated `offers` extension table. An offer is 1:1 with its case at any
  moment (a rejection-then-resubmission overwrites the same fields; there
  is no requirement anywhere in `MASTER_PROMPT.md` to keep a history of
  each submission attempt's exact text, only a history of the *state
  transitions*, which `case_events` already gives for free), so a second
  table would only add a join for no real benefit. Company name and
  contact don't need new columns at all — `Company.name`/`Company.contact`
  (M01) already cover BR-07's "company name" and "company contact."
- **Where the offer letter file lives, before M06 exists.** BR-07 requires
  "the offer letter file" to exist before a submission is valid, but the
  hardened upload pipeline (magic-byte sniffing, ClamAV, the authenticated
  streaming download route) is M06's explicit, later job — `MASTER_PROMPT.md`
  §7 puts M06 after M05 on purpose. `src/server/documents/store.ts` is a
  deliberately minimal interim writer: MIME allowlist check against
  `ALLOWED_MIME`, size check against `MAX_UPLOAD_MB`, a SHA-256 checksum, a
  UUID storage key, written to `UPLOAD_DIR` outside the web root — everything
  M06's own description already lists as *shared* infra (checksum,
  UUID filename, volume-not-webroot) — but explicitly **not** magic-byte
  sniffing, **not** a ClamAV scan, and **not** a download route. A
  `Document` row of type `OFFER_LETTER` gets created either way, so M06
  hardens the write path (add scanning, add sniffing) and adds the read
  path (the streaming download route) without changing this module's
  schema or its callers. Logged as a real scope boundary, not silently
  glossed over — see DECISIONS.md.
- **BR-09's "mandatory field... with the reason stored" reads as one
  field, not two.** Approval already requires a mandatory `reason`
  (M04's `requiresReason: true` on this row) — BR-09 is read as
  requiring that the *same* reason double as the relevance justification,
  plus a boolean `relevanceConfirmed` the Focal Person must explicitly set
  `true` (the "mandatory field" itself — omitting or sending `false`
  blocks approval). A second free-text "why is this relevant" field
  would duplicate the already-mandatory approval reason for no stated
  benefit. Revisit if this reading turns out wrong; adding a dedicated
  field later is additive.
- **BR-08's duration bounds stay config, not a DB CHECK.**
  `MIN_INTERNSHIP_WEEKS`/`MAX_INTERNSHIP_WEEKS` are environment
  configuration (`.env.example`), consistent with `RESTART_CAP` in M04 —
  a CHECK constraint can't reference an env var, so the bound is enforced
  only by the new `durationWithinBounds` guard. A plain sanity CHECK
  (`planned_end > planned_start` when both are set) is added at the
  database level as defence in depth, same pattern as always.
- **`case.open`'s business rule, beyond BR-06/BR-01.** BR-06's partial
  index (M01/M04) already blocks a second *non-terminal* case. It does
  **not** stop a student whose only case is already terminal from calling
  `case.open` again, and most terminal states shouldn't allow that: a
  `CLOSED_PASS` student has nothing left to do, and `CLOSED_INCOMPLETE`/
  `RESTART_DENIED`/`RESTART_AUTHORIZED` are exactly the states the
  restart gate (M10) owns — a plain re-open would let a student route
  around the gate entirely. The rule `openCase()` applies: **blocked from
  any terminal state except `WITHDRAWN`** (reusing M04's
  `TERMINAL_CASE_STATES` list minus `WITHDRAWN`, rather than enumerating
  the blocked states by hand) — a withdrawal happens before approval and
  leaves no grade (MASTER_PROMPT.md §1.2 gives no indication a withdrawn
  student is barred from trying again), so it's the one terminal state
  that's a genuine dead end otherwise. This conservatively also blocks
  `WAIVER_GRANTED`/`WAIVER_DENIED`, which per OQ-12 no transition ever
  actually produces today — dead code paths, but the safer default if
  that ever changes.
- **`ELIGIBILITY_PENDING → ELIGIBLE` finally gets a caller.** OQ-11's
  standing note said wiring this up "costs nothing beyond wiring up a
  caller" once a real one exists. `openCase()` is that caller:
  it creates the case in `ELIGIBILITY_PENDING` (the schema default), computes
  eligibility with M03's `computeEligibility()`, and only then calls
  `executeSystemTransition()` — so BR-01 ("eligibility computed from the
  roster, never self-declared") is enforced by the same guarded, audited
  code path as every other transition, not a special case. If the student
  isn't eligible, no case is created at all (a dangling
  `ELIGIBILITY_PENDING` row that can never advance would be worse than no
  row). OQ-11 updated to reflect this.
- **Rows 3 and 7 (`OFFER_SUBMITTED → OFFER_UNDER_REVIEW` and
  `APPROVED → IN_PROGRESS`, both `SYSTEM`, no guards) are chained
  automatically inside the same request**, not left for a scheduled
  sweep. Nothing in `MASTER_PROMPT.md` describes a meaningful waiting
  state between "student submitted" and "queued for review", or between
  "approved" and "internship under way" — the eight-step table lists them
  as immediate consequences, not scheduled events (contrast BR-02's
  semester-6 sweep, which explicitly *is* time-driven). `submitOffer()`
  calls both `executeTransition()` (STUDENT → `OFFER_SUBMITTED`) and
  `executeSystemTransition()` (→ `OFFER_UNDER_REVIEW`) in sequence;
  `approveOffer()` does the same for `APPROVED` → `IN_PROGRESS`. Each is
  still its own audited, guarded transition — chaining them in one
  function is a caller-convenience choice, not a shortcut around the
  executor.

## Data touched

One migration on the existing schema:

- `cases.work_description TEXT NULL`, with
  `CHECK (work_description IS NULL OR char_length(work_description) >= 200)`
  (BR-07, defence in depth alongside the `offerComplete` guard).
- `cases.relevance_confirmed BOOLEAN NULL` (BR-09).
- `CHECK (planned_end IS NULL OR planned_start IS NULL OR planned_end > planned_start)`
  on `cases` (sanity constraint; the actual week-bounds check is
  config-driven and lives only in the `durationWithinBounds` guard).

No other schema changes — `companies.name`/`companies.contact` (M01)
already cover BR-07's company fields, and `documents` (M01) already has
every column the interim upload writer needs.

## Business rules enforced

- **BR-01** (real, replacing M04's stub) — `eligibilityConfirmed` guard
  reads `computeEligibility()`'s result, passed in by `openCase()`.
- **BR-06** (partial, beyond M01/M04's index) — `openCase()`'s own
  terminal-state check, described above.
- **BR-07** (real, replacing M04's stub, used on both submission and
  resubmission) — `offerComplete` guard: offer letter document present,
  non-empty company name and contact, work description ≥ 200 characters.
  Also a DB CHECK on `work_description`'s length as defence in depth.
- **BR-08** (real, replacing M04's stub) — `durationWithinBounds` guard:
  planned end after planned start, and the gap between
  `MIN_INTERNSHIP_WEEKS` and `MAX_INTERNSHIP_WEEKS` (config, default 4–8).
- **BR-09** (real, replacing M04's stub) — `relevanceConfirmed` guard:
  the Focal Person must explicitly confirm relevance (`true`) to approve;
  the already-mandatory approval reason is read as the required
  justification (see "Scope decisions").

## API routes

All mutating routes call `requireCapability()` before touching data
(enforced by the existing ESLint rule). Every route follows M02/M03's
"404, not 403" rule when a Student requests a case that isn't theirs.

| Method | Route | Capability | Notes |
|---|---|---|---|
| `POST` | `/api/cases` | `case.open` (STUDENT) | Creates the case, wires BR-01 for real. 201 on success; `409 case_already_open` / `409 cannot_reopen` / `422 not_eligible`. |
| `GET` | `/api/cases` | `case.view_any` (FOCAL/HOD/DEAN) | Review queue; optional `?state=` filter. |
| `GET` | `/api/cases/:id` | `case.view_own` / `case.view_any` | Same ownership pattern as `GET /api/students/:id`. |
| `POST` | `/api/cases/:id/offer` | `case.open` (STUDENT, owner only) | Multipart: `companyName`, `companyContact`, `workDescription`, `offerLetter` file. Works for both first submission (`ELIGIBLE → OFFER_SUBMITTED`) and resubmission (`OFFER_REJECTED → OFFER_SUBMITTED`) — the executor picks the right table row from the case's current state. |
| `POST` | `/api/cases/:id/approve` | `offer.approve` (FOCAL) | JSON: `reason`, `plannedStart`, `plannedEnd`, `relevanceConfirmed`. Chains straight through to `IN_PROGRESS`. |
| `POST` | `/api/cases/:id/reject` | `offer.approve` (FOCAL) | JSON: `reason`. |

## Test list

- `unit/guards.test.ts` (extended) — `eligibilityConfirmed`,
  `offerComplete`, `durationWithinBounds`, `relevanceConfirmed`: pass and
  fail paths, no database.
- `unit/company-normalize.test.ts` — `normalizeCompanyName()` pure
  function: case/whitespace insensitivity, no database.
- `integration/BR01_case_open_requires_eligibility.test.ts` — an
  ineligible student's `openCase()` throws and creates no row; an
  eligible student's succeeds and lands the case on `ELIGIBLE` via a real
  `case_events` row (`ELIGIBILITY_PENDING → ELIGIBLE`).
- `integration/BR06_case_reopen_after_terminal_states.test.ts` —
  `openCase()` rejects re-opening from each of `CLOSED_PASS`,
  `CLOSED_INCOMPLETE`, `RESTART_DENIED`, `RESTART_AUTHORIZED`, and an
  existing non-terminal case; succeeds from `WITHDRAWN`.
- `integration/BR07_offer_requires_completeness.test.ts` — submission
  rejected for a missing file, missing company name, missing contact,
  and a work description under 200 characters; succeeds at exactly 200.
  Also covers the resubmission path from `OFFER_REJECTED`.
- `integration/BR08_duration_within_bounds.test.ts` — approval rejected
  for a duration under `MIN_INTERNSHIP_WEEKS`, over `MAX_INTERNSHIP_WEEKS`,
  and for an end date not after the start date; succeeds within bounds.
- `integration/BR09_relevance_confirmation_mandatory.test.ts` — approval
  rejected when `relevanceConfirmed` is omitted or `false`; succeeds when
  `true`.
- `integration/M05_offer_route_ownership.test.ts` — a Student can't open,
  submit for, approve, or reject another student's case (404s); a Focal
  Person can view and approve/reject any case; an unauthenticated request
  gets 401.
- `integration/M05_happy_path.test.ts` — the whole arc through one real
  HTTP-shaped call sequence: open → submit → (auto) under review →
  approve → (auto) in progress, asserting the resulting `case_events` row
  sequence matches rows 1–4 and 7 of M04's table exactly.

## Done criteria

1. An approval cannot be recorded without a reason and `relevanceConfirmed: true`
   (`MASTER_PROMPT.md`'s own stated done criterion for this module).
2. BR-01, BR-07, BR-08, BR-09 all have real guards; no stub remains on
   rows 1, 2, 4, 6 of the transition table.
3. `openCase()` wires row 1 for real — OQ-11 updated.
4. Every business rule above has a named test (`BR0X_*`), including a
   negative case.
5. `docker compose up --build` succeeds from a clean volume state, with
   the whole happy path exercised against the real stack, not just tests.
6. `/docs/PROGRESS.md` updated, M05 checked off.
