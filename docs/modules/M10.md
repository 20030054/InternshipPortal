# M10 — The restart gate

## Purpose

The workflow around the restart guards M04 already built for real (G1
different organisation, G2 time remains, G4 restart cap, G5 distinct
signers — see `docs/modules/M04.md` "Division of labour with M05/M09/M10").
M10's own job, per `MASTER_PROMPT.md` §7's module summary: "Restart
request, the four guards, dual sign-off from separate sessions, denial
and Dean escalation, restart cap, linked case creation (BR-16 to
BR-20)." Concretely: the routes that let a Focal Person initiate a
restart, an HoD counter-sign or deny it from a separate session, a Dean
rule on an escalated denial, and the genesis insert of the new linked
case once `RESTART_AUTHORIZED` fires. Also finishes G1's fuzzy-match
half, explicitly left to this module by `differentOrganization`'s own
doc comment (M04): "matching above `COMPANY_MATCH_THRESHOLD` with human
confirmation on a flagged match is M10's job."

**Depends on:** M01 (`RestartRequest`/`Escalation`, both unused until
now), M04 (all four guards, real since M04, first real callers here),
M03 (`computeEligibility()`, extended here for the graduation boundary).

## Scope decisions this module makes

- **G1's fuzzy-match/override half is workflow, not a guard change
  beyond registration number.** `differentOrganization` (M04) already
  hard-blocks an *exact* normalised-name match. This module extends it
  to also hard-block an exact `registrationNumber` match when both
  companies have one on file (`Company.registrationNumber` — M01,
  unused by any route until now; `findOrCreateCompany` gains an optional
  `registrationNumber` input, used only by the restart-request route,
  since BR-07's offer submission never collected one and stays that
  way). The *fuzzy* half (similarity above `COMPANY_MATCH_THRESHOLD` but
  not exact) can't be a guard at all in this architecture — guards are
  pure boolean pass/fail evaluated once, and "flagged, pending an
  explicit HoD override" is a two-step, stateful thing a boolean can't
  express. It lives in `src/server/companies/match.ts` (new,
  dependency-free Levenshtein-ratio similarity — the codebase has no
  fuzzy-match library and this is a five-line function, not worth a new
  dependency) and in the restart service: a flagged match doesn't block
  `RESTART_REQUESTED` (G1 the *guard* still only checks exact matches),
  but the countersign route then requires the HoD to pass
  `acknowledgeFlaggedMatch: true` alongside their reason, or it 400s.
  This makes BR-17's "a flagged match requires an explicit override
  reason from the HoD" a real, machine-checked requirement rather than
  reusing the ordinary signature reason silently.
- **A hard guard failure at request time still creates a `RestartRequest`
  row, with `outcome: DENIED`, not just a bare 409.** M04's transition
  table gates G1 (exact match)/G2/G4 directly on
  `CLOSED_INCOMPLETE -> RESTART_REQUESTED` — if any of them fails, the
  case never reaches `RESTART_REQUESTED` at all, so it can't later be
  moved to `RESTART_DENIED` by the HoD-deny transition either. But
  BR-18's "if any guard fails, the request is DENIED... it escalates to
  the Dean" has to mean something for *this* failure mode too, or a
  student blocked by the cap (BR-19: "on exceeding the cap, the only
  remaining route is a Dean-level ruling") would have no way to reach
  that ruling at all. Reading "the request" as the `RestartRequest` row
  itself (not `cases.state`) resolves this cleanly: every restart
  attempt — whether it dies at the door (G1/G2/G4) or later at explicit
  HoD review — produces exactly one `RestartRequest` row whose own
  `outcome` ends up `DENIED`, and *that* row is what `escalate` operates
  on. `cases.state` only moves to `RESTART_DENIED` when the failure
  happens at the second step (an HoD's explicit deny, or G5 — see next
  point); a first-step guard failure leaves the case sitting in
  `CLOSED_INCOMPLETE` exactly as M04 already built it, while still
  producing a real, escalatable, DENIED request record.
- **G5 (distinct signers) is not treated as a permanent denial.** Unlike
  G1/G2/G4, a same-account countersign attempt isn't a fact about the
  request that a *different* HoD account re-trying would still hit — the
  guard fails because of who's calling, not what's being requested. The
  countersign route just lets `executeTransition`'s own
  `distinctSigners` guard reject it (409, same as every other guard
  rejection in this codebase), without touching `RestartRequest.outcome`
  or `cases.state` — the request stays `PENDING`, open for a different
  HoD account (or the same one, corrected) to countersign properly, or
  to be denied outright instead. No new state, no special-casing.
- **The graduation boundary (G2) needs a number `MASTER_PROMPT.md` never
  states.** `computeEligibility()` (M03) has no notion of "how many
  semesters are left" — only "how many are done." Added
  `GRADUATION_BOUNDARY_SEMESTERS = 8` to `src/server/roster/eligibility.ts`
  and a `semestersRemainingBeforeGraduation()` function built on the
  existing `semestersCompleted` output. §15's seed-data line —
  "students across semesters 3 to 8" — is the only textual anchor for a
  program length anywhere in the document, and 8 is consistent with a
  standard 4-year/8-semester BS program at a Pakistani university. This
  is inference from a demo-data hint, not a stated fact, so it's logged
  as OQ-13 rather than silently assumed; picking a *smaller* boundary
  would make G2 easier to fail (more restrictive for restart eligibility)
  but would contradict the seed data's own claim that semester 8 is a
  normal, still-enrolled semester, so 8 is both the textually-grounded
  and the appropriately restrictive choice available.
- **The new linked case starts at `ELIGIBLE` with no company, not
  pre-filled with the restart's vetted new company.** The pseudocode
  (§5.3) only specifies `previous_case_id` on the new case, nothing
  about `company_id`. Pre-filling it would let a restart skip BR-07/
  BR-09's offer-submission and relevance-approval steps for the new
  placement — the same two steps every other case must pass through.
  The student still has to `submitOffer()` for the new company through
  the ordinary M05 path; G1 only vetted that the company differs from
  the failed one, not that it's an approved placement yet. This is the
  more restrictive reading (skips no business rule) and keeps case
  genesis uniform: every case's `company_id` is set the same way,
  through the same route, regardless of how the case came to exist.
- **`escalations` gets the same append-only privilege hardening M09 gave
  `grade_reversals`.** A real gap, same shape as D-060: M01 revoked
  `UPDATE`/`DELETE` on `audit_events`/`case_events`/`grades` but never on
  `escalations`, even though its own doc comment already claims finality
  ("no further transition anywhere in the system reads or updates an
  escalation row once written"). Fixed in this module's migration.
- **`Escalation.subjectId` points at the `Case`, not the
  `RestartRequest`.** `EscalationSubjectType` has exactly one value,
  `RESTART_DENIED` — the same literal as the `CaseState` a case sits in
  when its restart was denied. Reading `subjectId` as "the case in that
  state" (not the request row) keeps a future HoD dashboard's "cases
  needing Dean attention" query a single lookup on `cases.state`, and
  matches the enum's own naming more directly than an indirect join
  through `restart_requests` would.
- **A denied `RestartRequest` can only be escalated once.** BR-18 calls
  the Dean's ruling "final." Enforced at the service level (a second
  `escalate` call on the same request 409s) rather than a DB constraint,
  since `escalations.subject_id` has no natural uniqueness the schema
  can express cleanly without assuming this reading in the migration
  itself — a defensible application-level check, not a database-level
  guarantee, and documented as such.

## The four routes

| Route | Actor | Effect |
|---|---|---|
| `POST /api/cases/:id/restart-request` | FOCAL (`restart.initiate`) | Computes G1 (exact + fuzzy)/G2/G4 live, attempts `CLOSED_INCOMPLETE -> RESTART_REQUESTED`. Always creates a `RestartRequest` row — `PENDING` on success, `DENIED` (with the failing guard's detail in `g1Result`/`g2Result`) if a guard rejects it. |
| `POST /api/restart-requests/:id/countersign` | HOD (`restart.countersign`) | Attempts `RESTART_REQUESTED -> RESTART_AUTHORIZED` (G5). Requires `acknowledgeFlaggedMatch: true` if the stored request is flagged. On success: updates the request to `AUTHORIZED` and creates the new linked `Case` (`ELIGIBLE`, `previousCaseId` set) in the same transaction, *after* the executor call succeeds — same ordering lesson as M09's `awardGrade()`. |
| `POST /api/restart-requests/:id/deny` | HOD (`restart.countersign` — denial is part of the same review action, no separate capability) | `RESTART_REQUESTED -> RESTART_DENIED`, no guards. Updates the request to `DENIED`. |
| `POST /api/restart-requests/:id/escalate` | DEAN (`escalation.rule_restart`) | Requires the request's `outcome` to already be `DENIED`. Creates one `Escalation` row (`subjectType: RESTART_DENIED`, `subjectId: caseId`). No case-state change — matches `Escalation`'s own "final, nothing reads it back" doc comment. |
| `GET /api/cases/:id/restart-requests` | FOCAL/HOD/DEAN (`case.view_any`) | Lists a case's restart request history — mirrors M09's `GET /api/cases/:id/verifications`. |

## Business rules enforced

- **BR-16** — the transition table (M04) already restricts
  `RESTART_REQUESTED` to originate only from `CLOSED_INCOMPLETE`; no
  other route in this module ever calls `executeTransition` toward it.
- **BR-17** — G1 (exact name/registration hard-block, fuzzy flag +
  override), G2 (`semestersRemainingBeforeGraduation() >= 1`), G3/G5
  (dual sign-off, distinct accounts, both with mandatory reasons — M04's
  `requiresReason: true` plus `distinctSigners`).
- **BR-18** — every failed attempt produces a `DENIED` `RestartRequest`,
  escalatable exactly once, no retry path re-using the same request.
- **BR-19** — `belowRestartCap` (M04) fed a live `existingRestartCount`
  computed here as `count(RestartRequest where outcome=AUTHORIZED and
  failedCase.studentId = this student)` — covers the whole restart
  chain regardless of hop count, not just the immediate failed case.
- **BR-20** — the new `Case` row: fresh `INSERT`, `previousCaseId` set,
  the failed case is never touched beyond the transition executor's own
  `RESTART_AUTHORIZED` write.

## Done when

Every guard has a passing negative test (G1 exact name, G1 exact
registration number, G1 fuzzy-flag-without-override, G2 no time
remains, G4 cap reached, G5 same signer) and no code path creates a
second `Case` row without passing through `RESTART_AUTHORIZED` first —
proved by grepping for every `prisma.case.create` call site in the
restart module and confirming each is reached only from
`countersignRestart()`, itself only reachable after
`executeTransition(..., "RESTART_AUTHORIZED", ...)` resolves.
