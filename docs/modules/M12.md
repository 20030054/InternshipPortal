# M12 — Notifications and SLA escalation

## Purpose

Templated, versioned email for every status change (no ad-hoc strings
in services), BullMQ jobs for delivery and reminders, BR-27's Focal
Person SLA escalation, BR-28's supervisor non-response escalation
(M08 already built the detection logic — `classifyTokenForReminder()`
— leaving only delivery to this module, per its own doc comment), and
a digest email for the HoD.

**Depends on:** M01 (`Notification`, unused until now), M02
(`sendMail()`/`MailMessage`, the one-off transport this module doesn't
replace — see Scope decisions), M04 (the transition executor — this
module's single integration point for "every status change"), M08
(`classifyTokenForReminder()`, `recordReminderSent()`).

## Scope decisions this module makes

- **One integration point for "every status change," not six.**
  `executeTransition()` (M04) is the *only* code path that ever writes
  `cases.state` — every one of M05 through M11's transitions already
  flows through it. Rather than editing six already-shipped, already-
  tested service files to add a notification call after each of their
  own `executeTransition()`/`executeSystemTransition()` calls (real risk
  of missing one, or of a regression in code that's already proven
  correct), this module adds exactly one hook at the end of
  `executeTransition()` itself: after a transition's DB work commits, it
  enqueues a `case-notifications` job carrying the `CaseEvent` id and
  `emitsEvent` the transition just wrote. A worker handler looks up
  whether `src/server/notifications/templates.ts`'s registry has an
  entry for that `emitsEvent`; if not, it's a silent no-op — a small
  number of internal/redundant events are deliberately mapped to no
  recipients (see the registry's own comments for which, and why) rather
  than the registry being incomplete.
- **Genesis inserts (BR-02's sweep, M10's restart, M11's waiver) don't
  go through `executeTransition()` and so don't get the hook.** BR-02's
  sweep is a background job with no human waiting on an email. M10's new
  linked case's arrival is already covered by the *old* case's
  `RESTART_AUTHORIZED` notification (same information, one email, not
  two). M11's waiver genesis insert is the one gap worth closing
  directly: `initiateWaiver()` gets one explicit notification call (HoD
  needs to know a waiver is awaiting their countersignature from the
  moment it's requested, not just once the Dean's turn comes) — a
  small, targeted addition to a module this session already built,
  not a new pattern.
- **Delivery is decoupled from the request/response cycle.** Sending
  synchronously inside `executeTransition()` would make a slow or down
  SMTP relay stall an approve-offer/award-grade/etc. API call. The hook
  only enqueues; a BullMQ worker sends. `Notification.status` starts
  `QUEUED`, becomes `SENT` or `FAILED` after the worker's one attempt —
  deliberately `attempts: 1`, no automatic BullMQ retry. A failed
  send is logged as `FAILED` and visible (M13's eventual dashboard, or
  a direct query today) rather than silently retried hours later for an
  email whose content may already be stale by then. This is a judgement
  call, not specified by BR-26/27, and is the more honest failure mode:
  a retried job would either duplicate a `Notification` row per attempt
  (polluting the one place BR-27/28 need a clean "was this already
  sent" answer) or need extra bookkeeping to update the same row across
  attempts for no clear benefit.
- **`case.view_any`'s three roles (FOCAL/HOD/DEAN) are notified by role,
  not by per-case assignment.** No case has an "assigned" Focal Person,
  HoD or Dean anywhere in this schema — the whole authority matrix is
  role-based, not assignment-based (MASTER_PROMPT.md §2/§3). Every
  notification meant for staff goes to *every* user currently holding
  that role. For a single-Focal-Person department this is invisible;
  for a larger one it means everyone with the role sees everything,
  which is the safer default (nobody's phone silently drops a
  notification because of an unstated assignment rule this build
  doesn't have).
- **BR-27's "an approval or verification pending" is `OFFER_UNDER_REVIEW`
  and `PENDING_VERIFICATION`, and only those two.** Every other state a
  case can sit in either isn't Focal-pending (`ELIGIBLE`,
  `OFFER_REJECTED` — waiting on the student) or is transient/auto-
  chained the instant it's entered (`OFFER_SUBMITTED`, `APPROVED` —
  both immediately walked forward by a `SYSTEM` transition in the same
  service call, per M05's `submitOffer()`/`approveOffer()`, so a case
  never actually rests there long enough for an SLA clock to matter).
- **"Working days" excludes only Saturday/Sunday — no BNU holiday
  calendar.** `MASTER_PROMPT.md` never lists one, and none exists
  anywhere in this build's scaffolding. Not excluding extra holidays is
  the more restrictive reading for BR-27's purpose (the clock keeps
  running through a public holiday, giving the student *more*
  protection, not less) — logged as **OQ-14**, since a real BNU holiday
  calendar would be a legitimate, additive refinement.
- **The Focal SLA sweep and its "already escalated" check are scoped to
  the *current stay* in the pending state, not the case's whole
  history.** `OFFER_UNDER_REVIEW` is re-enterable (a rejected-then-
  resubmitted offer cycles through it again). Querying
  `Notification` for an escalation sent *since the most recent
  `CaseEvent` that entered this state* — not merely "ever, for this
  case" — is what keeps a stale escalation from an earlier review cycle
  from silently suppressing a real one in a later cycle.
- **The HoD digest reports only what this module tracks — current
  Focal-SLA breaches and supervisor-escalated cases — not the fuller
  "counts by state, all waivers, all restarts" picture.** That's M13's
  explicit job (§7's own module summary). Skipped entirely (no email
  sent) on a day with nothing to report — a guaranteed-empty daily email
  trains the recipient to stop reading it, defeating its own purpose.
- **`sendMail()` (M02) is left in place, untouched, for its one caller
  (password reset).** M12 doesn't retrofit the templating system onto
  it — a security-flow email with its own urgency/wording is a
  reasonable exception, exactly as M02's and M08's own doc comments
  already anticipated ("M12 replaces this... M02 needs exactly one
  email and shouldn't build that system early just to send it" — that
  system now exists, but nothing requires migrating M02's one call to
  use it, and doing so isn't needed for anything this module's done-
  criterion asks for).

## The templated notification system

`src/server/notifications/templates.ts`: a registry keyed by
`emitsEvent` (the transition table's own stable identifier — reused
rather than inventing a parallel naming scheme), each entry a
`{ id, version, recipients, render(context) }` — `render` returns
`{subject, text}`, pure and unit-testable like every other pure function
in this codebase. `id`/`version` are what land in
`Notification.templateId`/`templateVersion` — the literal "templated
and versioned" BR text.

`src/server/notifications/service.ts`: `sendNotification()` resolves
recipients (by role, or "the student on this case"), and for each,
creates a `Notification` row (`QUEUED`) before attempting `sendMail()`,
then updates it to `SENT`/`FAILED`. `dispatchTransitionNotification()`
is the `case-notifications` worker handler: loads the `CaseEvent`,
looks up the template for its `emitsEvent`, calls `sendNotification()`.

## BR-27 / BR-28 / digest

- `src/server/sla/focal-sla.ts`: pure `workingDaysElapsed()`,
  `isFocalSlaBreached()`. `src/server/sla/service.ts`:
  `runFocalSlaSweep()` — queries every case in `OFFER_UNDER_REVIEW`/
  `PENDING_VERIFICATION`, computes working days since the most recent
  entry into that state, escalates (one notification per `HOD` user,
  deduplicated per stay) once breached.
- `src/server/sla/service.ts`: `runSupervisorReminderSweep()` — queries
  every live (`usedAt IS NULL`, `revokedAt IS NULL`) `SupervisorToken`,
  calls M08's `classifyTokenForReminder()`, sends the first/second
  reminder to the supervisor's own email or the escalation to every
  `FOCAL` user, then calls `recordReminderSent()`.
- `src/server/sla/service.ts`: `runHodDigest()` — one email per `HOD`
  user summarising current Focal-SLA breaches and supervisor-escalated
  cases, skipped entirely when there's nothing to report.
- `worker/index.ts`: three new repeatable schedules
  (`sla-escalation-sweep`, `supervisor-reminder-sweep`, `hod-digest`),
  same `upsertJobScheduler` pattern as the roster sweep, plus the
  event-driven `case-notifications` worker.

## Done when

An untouched pending approval escalates on schedule in a time-travelled
test: a case sitting in `OFFER_UNDER_REVIEW` past `SLA_DAYS` working
days (constructed via a `CaseEvent`/`Notification` timestamp fixture,
not real wall-clock waiting) produces exactly one HoD-escalation
`Notification` per `HOD` user when `runFocalSlaSweep()` runs, and
running it again immediately after produces zero more (already
escalated for this stay) — proved against the real database, not a
mock.
