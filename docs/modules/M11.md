# M11 — The waiver path

## Purpose

The three-signature exception path that skips the eight normal steps
entirely (BR-21 to BR-24): Focal Person initiates with a mandatory
≥300-character exceptional-circumstance narrative and supporting
documentation, HoD counter-signs, Dean gives final approval — any one of
the three refusing ends it. At most one waiver per student, ever
(BR-23, a hard DB constraint since M01). **Done when** a waiver cannot
be granted with two signatures.

**Depends on:** M01 (`Waiver`, unused until now — its
`waivers_circumstance_min_length` CHECK and unique `student_id` already
built), M04 (transition executor — this module adds new rows to its
table, the first since M04 itself shipped), M06 (`storeDocument()`,
`DocumentType.SUPPORTING_EVIDENCE` — scaffolded, unused until now).

## Resolving OQ-12: a waiver *does* drive real `cases.state` transitions

OQ-12 (raised in M04) asked whether the four `WAIVER_*` `CaseState`
values represent real transitions or whether the waiver workflow is
entirely independent of any `Case` row. M04 applied the restrictive
default (independent) because nothing forced an answer yet. Building
this module surfaced three pieces of concrete, pre-existing evidence
that settle it the other way — not a guess, a reading of what M01/M04
already committed to:

1. **M01's own partial unique index.** `cases_one_nonterternal_per_student`
   excludes `WAIVER_GRANTED`/`WAIVER_DENIED` from "non-terminal" —
   exactly alongside `CLOSED_PASS`/`CLOSED_INCOMPLETE`/`WITHDRAWN`/
   `RESTART_DENIED`. M01 would have no reason to carve out these two
   specific enum values in a hand-written index unless a real `cases.state`
   row was expected to hold them.
2. **M04's `TERMINAL_CASE_STATES` already lists them.**
   `src/server/state-machine/types.ts` includes `WAIVER_GRANTED`/
   `WAIVER_DENIED` — dead code until this module, since no transition
   ever produced them, but M04 clearly anticipated real rows reaching
   these states.
3. **`Document.caseId` is `NOT NULL`.** BR-22's "attach supporting
   documentation" needs somewhere to attach a `Document` row, and every
   `Document` requires a real `caseId`. A case-independent waiver would
   have nowhere for the evidence file to live without a schema change
   this module doesn't need to make.

**Resolution:** waiver initiation is a genesis insert (same pattern as
BR-02's sweep and M10's restart) — a fresh `Case` row, created directly
in `WAIVER_REQUESTED`, `previousCaseId` null, `companyId` null. Four new
rows join M04's transition table:

| # | From | To | Actor | Guards | Reason required |
|---|---|---|---|---|---|
| 22 | `WAIVER_REQUESTED` | `WAIVER_COUNTERSIGNED` | HOD | none | Yes |
| 23 | `WAIVER_REQUESTED` | `WAIVER_DENIED` | HOD | none | Yes |
| 24 | `WAIVER_COUNTERSIGNED` | `WAIVER_GRANTED` | DEAN | none | Yes |
| 25 | `WAIVER_COUNTERSIGNED` | `WAIVER_DENIED` | DEAN | none | Yes |

No guards: BR-22 (circumstance length, evidence attached) is enforced
at genesis-insert time, before any transition exists to guard; BR-23
(one waiver ever) is a hard, unconditional unique constraint on
`waivers.student_id` — not partial like `cases_one_nonterminal_per_student`,
so even a `DENIED` waiver blocks any future attempt for that student,
literally "ever." Nothing left for a transition guard to check.
`WAIVER_COUNTERSIGNED → WAIVER_GRANTED`/`WAIVER_DENIED` only being
reachable from `WAIVER_COUNTERSIGNED` (never directly from
`WAIVER_REQUESTED`) is what makes the three signatures sequential and
mandatory — the Dean cannot rule before the HoD has.
`OPEN_QUESTIONS.md`'s OQ-12 row moves to the resolution log.

## Scope decisions this module makes

- **Case creation happens *before* the supporting-evidence document is
  stored, with an explicit compensating delete on failure.**
  `initiateWaiver()` creates the `Case` row first (nothing else can
  reference a `caseId` that doesn't exist yet — `Document.caseId` is
  required), then calls `storeDocument()`. If that fails (bad file type,
  infected, oversized — routine, expected failure modes, not a rare
  race), the just-created `Case` row is deleted before the error
  propagates. Without this, a failed upload would leave a permanent,
  unrecoverable orphan: `waivers.student_id` is uniquely constrained, so
  a retry after fixing the file would find the student "already has a
  waiver" — the exact class of bug M09's `awardGrade()` ordering fix
  caught (D-057), one step earlier in the pipeline. Deleting a genesis
  `Case` row is otherwise unprecedented in this codebase (every other
  module only ever transitions, never deletes) — safe here specifically
  because this row never passed through the transition executor and
  nothing else can have referenced it yet (the `Waiver` row itself is
  only created *after* the document succeeds).
- **The `Waiver` row is created only after both the `Case` genesis
  insert and the supporting document succeed**, in one transaction with
  its own `AuditEvent` (`WAIVER_INITIATED`). Mirrors BR-02's sweep and
  M10's restart genesis-insert shape exactly.
- **No student-facing waiver view in this module.** BR-21 to BR-24 never
  ask for one — a rendered "eight-step progress line" (or its waiver
  equivalent) is M13's job. `GET /api/waivers` (staff-only, reusing
  `case.view_any`) is the "permanent visibility" BR-24 asks for at this
  module's scope; the HoD-dashboard aggregation and annual-report export
  are also M13's job. Building a full dashboard now would guess at UI
  shape nothing in this module's done-criterion needs.
- **`case.view_any` covers waiver visibility; no new `waiver.view`
  capability.** Same reasoning M09 (`grade.reverse`) and M10
  (`escalation.rule_restart`) used for a genuine capability gap — but
  this isn't a gap: `case.view_any` ("FOCAL/HOD/DEAN can view any case")
  already covers exactly the roles BR-24 names, and a waiver is now a
  real `Case` row. Reusing it, not inventing a twentieth capability.
- **One supporting-evidence file per waiver, not a list.** BR-22 says
  "attach supporting documentation" without specifying single or
  multiple files. Mirrors M05's single-offer-letter-file shape — the
  restrictive, unguessed default. Additive if the Focal Person/HoD later
  need more than one (loop `storeDocument()` calls, no restructuring).
- **`circumstance` (the ≥300-character narrative) and each signer's own
  `reason` are separate fields**, matching the `Waiver` schema's own
  shape (`circumstance` once; `focalReason`/`hodReason`/`deanReason`
  each nullable, one per signature). The narrative is written once at
  initiation; each signer still gives their own short reason for
  countersigning, denying, or approving — same "mandatory reason per
  signature" pattern as the restart gate's G3.

## Business rules enforced

- **BR-21** — genesis insert reachable only via `waiver.initiate`
  (FOCAL); three sequential signatures via rows 22-25; any refusal
  (`WAIVER_DENIED`, reachable from either the HoD or the Dean stage)
  ends it with no retry (BR-23 makes retry structurally impossible).
- **BR-22** — `circumstance` zod `.min(300)` at the service layer plus
  `waivers_circumstance_min_length` CHECK (M01) as the floor a direct
  SQL write can't get under; supporting documentation via
  `storeDocument()` with `type: SUPPORTING_EVIDENCE`.
- **BR-23** — `waivers.student_id UNIQUE` (M01, unconditional — no
  partial-index carve-out), backed by an application-level pre-check for
  a clean error before the DB constraint would otherwise 500.
- **BR-24** — `GET /api/waivers` (staff, `case.view_any`) — see scope
  decisions for why this is the whole of this module's visibility story.

## Done when

A waiver cannot be granted with two signatures — proved by an
integration test asserting `WAIVER_COUNTERSIGNED → WAIVER_GRANTED`
requires the DEAN role specifically (a HOD attempting it 403s, and no
path reaches `WAIVER_GRANTED` from `WAIVER_REQUESTED` directly). Every
guard/precondition gets a negative test: circumstance under 300 chars,
missing evidence file, a second waiver attempt for the same student
(both a clean pre-check 409 and, separately, proof the DB constraint
itself would catch it), HoD denial, Dean denial, wrong-role attempts at
each of the three stages.
