# M00 — Repository and container skeleton

## Purpose

Stand up the empty shell everything else builds inside: a runnable,
containerised Next.js app behind Caddy, with the full Compose topology
present (even where later modules are what actually populate a service),
CI that runs lint/typecheck/tests, and the docs scaffold this session
already created. Nothing in M00 implements a business rule — it exists so
that from M01 onward, every module lands into a working build instead of
bootstrapping infrastructure alongside logic.

## Data touched

None. No Prisma schema yet (that's M01). Postgres and Redis containers run
empty — just present and healthy.

## Business rules enforced

None directly. M00 is the substrate BR-26 (audit privilege separation) and
the trigger-based rules in §9 will later depend on (two DB roles, named
volumes, non-root containers) — so the *shape* of the infrastructure must
already respect those constraints even though no rule is testable yet:

- Postgres and app containers run as non-root.
- The Compose file already declares the two-role DB pattern's plumbing
  (i.e., `DATABASE_URL` for the app and a separate migration connection
  string), even though M01 is what creates the roles themselves.
- `scit_uploads` exists as a named volume from the start, never a bind
  mount, even though nothing writes to it yet.

## Scope

### Repository layout

Per `/docs/CONVENTIONS.md` §"Repository layout": single Next.js app at the
root, `/src`, `/prisma`, `/tests`, `/docs` (already present).

```
package.json, pnpm-lock.yaml
tsconfig.json               strict: true
.eslintrc / eslint.config.js  + eslint-plugin-security
.prettierrc
next.config.ts
Dockerfile                  multi-stage: deps -> build -> runtime (slim, non-root)
docker-compose.yml
.dockerignore
.env.example
/src/app/page.tsx           minimal "hello" page (temporary, replaced by M13's real home page)
/src/app/api/health/route.ts
/src/app/api/ready/route.ts
Caddyfile
/.github/workflows/ci.yml   or equivalent — lint + typecheck + test on push
```

### Dockerfile requirements

- Multi-stage: a `deps`/`build` stage with full devDependencies, a
  `runtime` stage that copies only the production build output and
  `node_modules` (via `next build` standalone output).
- Runtime stage runs as a created non-root user (e.g. `appuser`, uid
  10001), owning `/data/uploads` inside the container even though nothing
  writes there until M06.
- No secrets baked into the image. `.dockerignore` excludes `.env*`,
  `.git`, `node_modules`, `docs/`.
- Same image is used for both `app` and `worker` services; `worker`
  overrides the `command` (the actual BullMQ consumer entrypoint is a
  no-op placeholder until M12 — it should start, log "worker ready", and
  stay alive, not implement job processing yet).

### docker-compose.yml — all seven services present

`caddy`, `app`, `worker`, `postgres`, `redis`, `clamav`, `backup`, matching
the topology in `/docs/ARCHITECTURE.md` §3:
- Only `caddy` publishes ports (80/443).
- `postgres`, `redis`, `clamav` have no published ports.
- Every service has a `healthcheck` and `restart: unless-stopped`.
- `app` and `worker` `depends_on` postgres and redis with
  `condition: service_healthy`.
- Five named volumes declared: `scit_pgdata`, `scit_uploads`,
  `scit_redis`, `scit_backups`, `scit_caddy`.
- `backup` service exists in the compose file with a placeholder cron
  script that only logs (real `pg_dump` logic lands with M01's schema to
  dump).

### Caddy

Minimal `Caddyfile` reverse-proxying `app_url -> app:3000`, automatic HTTPS
for a real domain, with a documented fallback to an internal/self-signed
cert for campus-network-only deployment (comment in the Caddyfile, not a
second file, to avoid config drift).

### Health endpoints

- `GET /api/health` — liveness only: process is up, returns `200 {status:
  "ok"}`. No dependency checks.
- `GET /api/ready` — readiness: checks DB connection and Redis connection,
  returns `200` only if both respond, `503` otherwise with which dependency
  failed. (At M00 the DB check can be a trivial `SELECT 1` against an empty
  database — the schema doesn't need to exist yet for connectivity to be
  provable.)

### CI script

Single workflow/script running, in order: install (frozen lockfile) → lint
→ typecheck (`tsc --noEmit`) → unit tests (Vitest, even if the only test at
this point is a trivial health-endpoint test). Fails the build on any
non-zero exit. This is also where the "every mutating route calls
`requireCapability()`" CI lint rule from §9 will eventually be wired in —
not yet, since there are no mutating routes, but note the hook point here
so M02 doesn't have to rediscover where CI lives.

### .env.example

Every variable from `MASTER_PROMPT.md` §8.2, each commented, no values
filled in. Present from M00 even though most are unused until later
modules — this avoids every later module having to remember to add its own
key to a file it might not think to touch.

## Test list

- `health.test.ts` — `GET /api/health` returns 200.
- `ready.test.ts` — `GET /api/ready` returns 200 when DB+Redis are up, 503
  with a body identifying the failed dependency when one is down (can be
  simulated by pointing `DATABASE_URL` at a closed port in the test).
- CI smoke: a script-level check (not Vitest) that `docker compose config`
  validates without error, and that the Dockerfile builds.

## Done criteria

1. `docker compose up --build` from a clean volume state serves the
   placeholder page over HTTPS (or the documented internal-cert fallback)
   via Caddy.
2. `GET /api/health` and `GET /api/ready` both return correctly.
3. `app` and `worker` run as non-root and only `caddy` has published ports.
4. CI runs lint + typecheck + tests and fails the build if any step fails.
5. `.env.example` contains every variable from §8.2 with no values.
6. `/docs/PROGRESS.md` updated, M00 checked off.
