# M15 — Action-taking UI (post-master-prompt addition)

## Purpose

Not one of `MASTER_PROMPT.md` §7's fifteen modules — M13 built every
dashboard as deliberately read-only (D-083: "action-taking forms for
the routes M05-M11 already built are a real, separable follow-on, not
something [M13's] own done-criterion needs"), and M00 through M14
together cover every business rule, security requirement and ops
procedure the master prompt actually asks for. This module closes the
one gap that isn't a master-prompt requirement but is what makes the
system a walkable product rather than an API with dashboards bolted
on: a case can be viewed from four different screens, but nowhere
could anyone actually *do* anything to it without calling the API
directly.

## Scope: the normal eight-step path only

`MASTER_PROMPT.md` §1.2 draws its own line between the normal path and
"three exception paths" (restart, waiver, withdrawal). This module
builds forms for the eight normal-path actions only — every one of
them already has a real, tested API route from M05-M09; this module
adds zero new server-side logic, only UI that calls what exists:

| Step | Actor | Action | Route |
|---|---|---|---|
| 1→2 | Student | Open case | `POST /api/cases` |
| 2 | Student | Submit offer letter | `POST /api/cases/:id/offer` |
| 3 | Focal | Approve / reject offer | `POST /api/cases/:id/approve` \| `/reject` |
| 4 | Student | Log weekly progress | `POST /api/cases/:id/progress-log` |
| 5 | Student | Mark internship complete | `POST /api/cases/:id/complete-internship` |
| 5 | Student | Upload completion certificate | `POST /api/cases/:id/completion-certificate` |
| 5 | Focal | Issue supervisor evaluation link | `POST /api/cases/:id/supervisor-token` |
| 6 | Focal | Verify a deliverable | `POST /api/documents/:id/verify` |
| 6 | Focal | Mark case fully verified | `POST /api/cases/:id/mark-verified` |
| 7 | Focal | Recommend grade | `POST /api/cases/:id/recommend-grade` |
| 7 | HoD | Award grade (final) | `POST /api/cases/:id/award-grade` |

**Explicitly out of scope this pass:** restart-gate forms (initiate/
counter-sign/deny/escalate), waiver-path forms (initiate/counter-sign/
approve/deny), and grade reversal. Real, valuable, and a natural
follow-on in the same shape — not built now to keep this module's own
scope honest and finishable. Every one of those routes is already
fully tested and reachable via the API/RUNBOOK today.

## Design decisions

- **No new server-side code.** Every form is a thin client component
  that `fetch()`s an existing, already-tested `/api/**` route with
  `credentials: "same-origin"` — the CSRF middleware (M14) already
  requires this and already works for exactly this shape of call.
  Introducing Next.js Server Actions was considered and rejected: it
  would create a second mutation pathway bypassing the CSRF/rate-limit
  middleware's `/api/**`-scoped matching and the route-handler-direct-
  call integration test pattern this entire codebase's test suite is
  built on.
- **A new case detail page, not more dashboard columns.** `/cases/:id`
  — same ownership pattern as every other per-case route (`case.
  view_own`/`case.view_any`, 404 not 403). Dashboard rows link into it
  rather than each dashboard growing bespoke inline actions.
- **Coarse state filtering only, never guard duplication.** The page
  decides which action *components* to render using each capability
  the current user's roles hold (already known, cheap) plus the
  case's raw `state` compared against the real transition table
  (`src/server/state-machine/transitions.ts`, imported, not
  re-derived) — never re-implementing BR-07 through BR-14's actual
  guards. `MASTER_PROMPT.md` §9 says it directly: "the UI hides what
  the API forbids — but the API forbidding it is the control." If
  state has moved on between page load and submit, the real API
  rejects it and the form shows that real error, not a UI-invented one.
- **`SHOW_EVALUATION_TO_STUDENT` respected in the detail page's own
  data-fetching**, mirroring `GET /api/cases/:id/evaluation`'s
  existing behaviour, not re-deciding it.

## Done when

Every normal-path action in the table above is reachable from a real
page as the correct role, on a case in the correct state, and produces
the exact same result calling the route directly would. `pnpm exec tsc
--noEmit`, `pnpm lint`, `next build` all clean. A real `docker compose`
walkthrough moves one live case from `ELIGIBILITY_PENDING` through
`CLOSED_PASS` using only the rendered pages' own request shapes (proven
by replaying each form's exact fetch payload against the real running
stack), confirming each role sees only the actions its capabilities
allow.
