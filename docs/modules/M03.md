# M03 — Roster, semesters and the eligibility engine

## Purpose

Replace "eligibility is whatever the student claims" with "eligibility is
a fact computed from the registrar's roster" (BR-01), and replace "a
student can fall through the cracks silently" with an automatic,
login-independent safety net (BR-02). This module also gives the Admin
role its two `users.manage`-gated operational levers named in
`MASTER_PROMPT.md` §2.6: roster import and semester open/close.

**Depends on:** M01 (schema, migration pattern), M02 (`requireCapability`,
the `users.manage` capability already in the matrix, the Admin role).

## Scope decisions this module makes

- **OQ-06** (roster source/format) is unanswered. Implements CSV only,
  per the restrictive default already flagged in `PROGRESS.md` ("CSV as
  the safe default, universally exportable from any SIS"). XLSX is not
  built this session — `MASTER_PROMPT.md` §7 says "CSV/XLSX," not both
  are mandatory on day one, and adding an XLSX parser later is additive
  (a second branch in the same import route), not a rewrite.
- **OQ-01** (per-semester deadline dates) is unanswered. Semester
  configuration accepts a `documentDeadline` per semester (the column
  already exists, nullable, from M01) but nothing in this module invents
  a default value — an admin sets it explicitly per semester, or leaves
  it null, per M01's existing handling.
- **New question, OQ-11 — exactly when is a `Case` row created relative
  to eligibility?** `MASTER_PROMPT.md`'s 8-step table lists
  `ELIGIBILITY_PENDING` as a real case state ("1 | Check eligibility |
  System | `ELIGIBILITY_PENDING`"), which could mean every student gets a
  case at admission that later flips to `ELIGIBLE`. But BR-02's "a
  student who has **not opened** a case by the end of the 6th semester is
  auto-enrolled" only makes sense if, before that point, most eligible
  students *don't* have a case yet — "opening a case" reads as a student
  action (§3's `case.open` — one capability covering "open case / upload
  offer letter" together), which is M05's job, not M03's.
  Restrictive interpretation applied here: **M03 never auto-creates a
  case for the normal 4-semester eligibility path.** Eligibility is a
  pure computed value, exposed read-only; M05 is what creates a case
  (already `ELIGIBLE`, since the student could only open one after
  passing the eligibility check) when a student actually acts. The *one*
  case-creation M03 does perform is BR-02's semester-6 fallback, because
  the master prompt is explicit and unambiguous there: "the system
  creates a mandatory case." That fallback is a fresh `INSERT`, not an
  `UPDATE` of `cases.state` — so it needs no transition executor (M04's
  job) to do correctly; a trigger guarding `BEFORE UPDATE OF state` never
  fires on `INSERT`. Logged in `OPEN_QUESTIONS.md` as OQ-11; M04 should
  confirm or correct this reading once the full transition table exists.
- **Semester ordering is an explicit `sequenceNumber`, not
  type+year arithmetic.** Guessing "Fall precedes the following Spring
  precedes the following Summer" bakes in one academic-calendar
  convention that might not match BNU's actual one, and silently breaks
  if a semester is created out of the assumed order. An explicit,
  admin-assigned integer removes the guesswork.
- **"Current semester" is an explicit admin action (open/close), not
  inferred from today's date against `[startsOn, endsOn]`.** This is not
  a judgement call — `MASTER_PROMPT.md` §2.6 lists "open/close semesters"
  as a named Admin capability, so the mechanism is specified, not
  invented.
- **The worker becomes a real BullMQ consumer this module** (M00's
  heartbeat placeholder is replaced), and the Dockerfile changes from
  copying Next's pruned `standalone` output to copying the full
  `node_modules` from the builder stage, run via `tsx` instead of
  `node server.js`/plain `node`. See "Why the Dockerfile changed" below
  and `DECISIONS.md`.

## Data touched

New migration on the existing schema:

- **`semesters`** gains: `sequence_number` (int, unique, admin-assigned at
  creation — chronological order, not inferred), `status`
  (`SemesterStatus` enum: `UPCOMING` / `OPEN` / `CLOSED`, default
  `UPCOMING`). A partial unique index limits the whole table to at most
  one `OPEN` semester at a time, mirroring M01's
  `cases_one_nonterminal_per_student` mechanism.
- **`cases`** gains: `auto_enrolled` (boolean, default `false`) — set
  `true` only by the BR-02 sweep, so the HoD dashboard (M13) can query
  "all auto-enrolled cases" directly instead of parsing audit metadata.
- **`roster_imports`** (new table): `id`, `imported_by` (fk user),
  `filename`, `total_rows`, `created_count`, `updated_count`,
  `error_count`, `errors` (jsonb — `[{row, message}]`), `created_at`.
  Import provenance, in the same spirit as M01's `audit_events` but
  scoped to this one operation with a shape worth querying directly
  (a Registrar asking "what happened in Tuesday's import" shouldn't have
  to reconstruct it from generic audit rows).

No privilege-grant changes needed — M01's `ALTER DEFAULT PRIVILEGES`
already covers new tables, and `cases`/`semesters` already have full
`scit_app` grants.

## Business rules enforced

- **BR-01** — `src/server/roster/eligibility.ts`'s `computeEligibility()`:
  a student is eligible once they have `>= 4` **closed** semesters at or
  after their admission semester (by `sequenceNumber`). "Closed," not
  merely "elapsed by date," because §2.6's open/close mechanism is the
  system of record for what semester it currently is — see "current
  semester" above.
- **BR-02** — `src/server/roster/auto-enrollment-sweep.ts`: for every
  student with `>= 6` closed semesters since admission and **zero** case
  rows of any kind (checked, not just "no non-terminal case" — a student
  who never engaged at all has no case in *any* state), creates one
  `Case` row directly in `ELIGIBLE` (skipping `ELIGIBILITY_PENDING` — see
  OQ-11 above) with `autoEnrolled: true`, and writes an `audit_events` row
  attributed to `SYSTEM` with job name `roster-sweep`. Runs as a BullMQ
  repeatable job (no login involved) and is also triggerable on demand by
  an Admin for testing/ops.
- **BR-03** is not implementable yet — it depends on `CLOSED_PASS`/waiver
  states that only mean something once M04's transition executor and
  M09/M11's grading and waiver flows exist. Noted, not stubbed.
- **BR-04** — the graduation clock is **never a stored column**. It's the
  pure function `computeEligibility()` returns (`semestersCompleted`,
  `semestersUntilBoundary`, etc.), computed fresh on every read from
  `admissionSemesterId` and the current `OPEN` semester. This is what
  makes "read-only to every human role, including Admin — no API route
  may write to it" trivially true: there is no column to write to.
- **BR-05** — `semesters.document_deadline` (from M01) is set via the
  semester-configuration route. This module only stores the value;
  *flagging* a case for a missed deadline is M07/M09's job once
  documents and cases are real.

## API routes

| Route | Method | Mutating? | Capability | Purpose |
|---|---|---|---|---|
| `/api/admin/semesters` | GET | No | `users.manage` | List semesters, ordered by `sequenceNumber`. |
| `/api/admin/semesters` | POST | Yes | `users.manage` | Create a semester. `sequenceNumber` auto-assigned as `MAX(sequenceNumber) + 1` unless explicitly given (registrar backfilling history out of order). |
| `/api/admin/semesters/:id/open` | POST | Yes | `users.manage` | Sets this semester to `OPEN`; the previously `OPEN` semester (if any) moves to `CLOSED` in the same transaction — the partial unique index makes skipping this atomically impossible. |
| `/api/admin/semesters/:id/close` | POST | Yes | `users.manage` | Sets this semester to `CLOSED` without opening another (end of an academic year, before the next term starts). |
| `/api/admin/roster/import` | POST | Yes | `users.manage` | `multipart/form-data` CSV upload. Upserts `users`/`students` by `registrationNumber`; never deletes a student absent from a later import. Writes one `roster_imports` row per call. |
| `/api/admin/roster/sweep-now` | POST | Yes | `users.manage` | Manually triggers the BR-02 sweep (the same function the scheduled job calls) — for ops/testing, not a substitute for the schedule. |
| `/api/students/:id/eligibility` | GET | No | `student.view_own` / `student.view_any` | Extends M02's existing ownership pattern on the same route family: `{ semestersCompleted, isEligible, isPastAutoEnrollBoundary }`. |

## Screens

None. Roster import and semester configuration are Admin-only operational
tasks; M13 is where any of this gets a UI. This module is API + job only.

## Why the Dockerfile changed

M00 built the runtime image around `next.config.ts`'s `output:
"standalone"` — a pruned `node_modules` containing only what Next's file
tracer finds reachable from actual routes/pages. That was fine while the
`worker` service did nothing but write a heartbeat file (no npm
dependencies at all). This module gives the worker a real job: consuming
a BullMQ queue and running `src/server/roster/auto-enrollment-sweep.ts`
on a schedule — real TypeScript, sharing the same Prisma client and
business logic the API routes use, not a reimplementation.

Next's tracer only follows imports reachable from the Next.js app itself;
it has no way to know the separate `worker` process needs `bullmq` or
`tsx`, so standalone's pruned `node_modules` doesn't reliably contain
them. Rather than reimplement the sweep in worker-only plain JavaScript
(duplicating BR-02's logic in two places, one of them untyped) or stand
up a second build pipeline (a bundler for the worker entrypoint) — the
Dockerfile now copies the **full** `node_modules` from the `builder`
stage into `runtime`, and both `app` and `worker` run from it: `app` via
`node node_modules/next/dist/bin/next start` (no longer `node
server.js`), `worker` via `node node_modules/tsx/dist/cli.mjs
worker/index.ts` (no longer plain `node worker/index.mjs`). `tsx` runs
real TypeScript directly, so `worker/index.ts` can `import` from
`src/server/roster/*` exactly like a route handler does — which also
means the runtime image now has to carry the raw `src/` source tree and
`tsconfig.json` (for the `@/*` alias tsx resolves those imports through),
not just the compiled `.next` output the app itself runs from. That gap
surfaced immediately as `ERR_MODULE_NOT_FOUND` the first time the worker
actually started in a container — the `app`/`.next` split had genuinely
never needed raw `src/` present before this module.

Trade-off, stated plainly: the runtime image now carries devDependencies
(`typescript`, `eslint`, `vitest`, …) it doesn't execute, larger than a
truly pruned image would be. Acceptable for a self-hosted, single-tenant
university deployment where image size isn't a cold-start-sensitive
concern; M14 (hardening) can revisit with a proper worker bundler if a
leaner image ever becomes worth the added build complexity.

## Test list

- `unit/eligibility.test.ts` — `computeEligibility()` against a table of
  (admission sequence, current sequence, closed-semester count) cases:
  exactly 3 closed semesters since admission is not yet eligible; exactly
  4 is eligible; a semester still `OPEN` or `UPCOMING` never counts as
  closed regardless of its date range; exactly 6 closed semesters crosses
  the auto-enrollment boundary; 5 does not.
- `unit/csv-import-parsing.test.ts` — a well-formed CSV parses to the
  expected rows; a row missing a required column is reported as a row
  error, not a thrown exception that aborts the whole import; a
  duplicate `registrationNumber` within one file is reported, not
  silently overwritten twice.
- `integration/BR01_eligibility_is_computed_not_stored.test.ts` — no
  column anywhere on `cases` or `students` stores an eligibility flag
  (schema introspection); the same student's computed eligibility changes
  the instant the relevant semester's `status` flips to `CLOSED`, with no
  other write involved.
- `integration/BR02_auto_enrollment_sweep.test.ts` — a student with 6
  closed semesters and zero cases gets exactly one `ELIGIBLE` case with
  `autoEnrolled: true` after the sweep runs; running the sweep twice
  doesn't create a second case (BR-06's partial unique index would reject
  it, but the sweep's own query should never attempt it — tests the
  query, not just the constraint); a student with an existing case of any
  kind (including a terminal one) is never touched by the sweep, even
  past the boundary.
- `integration/M03_semester_open_close_exclusivity.test.ts` — opening a
  second semester while one is already `OPEN` closes the first
  atomically; two concurrent "open" requests can't both succeed (the
  partial unique index is the actual guarantee under test, hit directly
  with a raw conflicting `INSERT`/`UPDATE`, same style as M01's
  constraint tests).
- `integration/M03_roster_import.test.ts` — importing a CSV creates new
  students; re-importing the same file is idempotent (no duplicate
  students, existing rows updated not doubled); a `roster_imports` row is
  written with accurate counts; an admin-only capability check (a Focal
  session gets 403).
- `integration/M03_eligibility_route_ownership.test.ts` — same
  own/any pattern as M02's `/api/students/:id` test, now against
  `/api/students/:id/eligibility`.

## Done criteria

1. A student advancing from semester 3 to 4 (i.e., a 4th semester since
   their admission is marked `CLOSED`) becomes eligible with zero writes
   beyond that one `close` action — proven by test, not just by reading
   the pure function.
2. A student with 6 closed semesters and no case is auto-enrolled by the
   scheduled sweep with no login or admin action involved (proven with an
   injectable/fake clock or a directly-invoked job run, not a real wait).
3. Roster import is idempotent and capability-gated; a non-Admin session
   is rejected.
4. `docker compose up --build` succeeds from a clean volume state with
   the revised Dockerfile, and the `worker` service is confirmed to
   actually run `worker/index.ts` via `tsx` (not silently falling back to
   a stale cached image).
5. `/docs/PROGRESS.md` updated, M03 checked off.
